# 학습 기능 8종 단계별 개발 계획

작성일: 2026-11-23 (Asia/Seoul)

계획 기준: feature/system-imporove 브랜치의 4cb6bd0 및 확인 시점 작업 폴더. 현재 다른 작업의 미커밋 변경이 있으므로 본 문서는 기존 코드·SQL·진행 기록을 수정하지 않고 별도로 추가한다. 아래 신규 화면·테이블·API·파일 이름은 제안이다. 저장소에서 확인한 구현과 운영 배포·DB 적용 상태를 구분하며, 이 계획 작성 중 테스트나 운영 마이그레이션을 실행하지 않았다.

## 1. 목표와 최종 사용자 흐름

자료 등록 → 학습 준비 → 자기 설명·퀴즈 → 어려운 개념을 이슈로 기록 → 설명 개선 → 독립 재평가 → 다음 복습 예약 → 브리핑·캘린더 추천 → 개념별 학습 이력 누적.

첫 배포 목표는 대시보드 → 복습 관리 → 실제 학습 → 결과 갱신의 연결이다. 학습 메이트·준비 자동화·장기 관계 그래프·외부 연동은 뒤 단계에서 연결한다.

| 화면 | 최종 역할 | 연결 기능 |
| --- | --- | --- |
| 대시보드 / | 지금 할 일 결정 | 학습 브리핑, 이어서 학습, 오늘 복습·이슈 요약 |

## 3. 개발 단계와 의존 관계

| 단계 | 개발 묶음 | 선행 조건 | 검토 가능한 결과물 |
| --- | --- | --- | --- |
| 0 | 기준선·화면·저장 계약 확정 | 없음 | 현재 구현/미구현 목록, 경로·상태·이벤트 계약 |
| 1 | 브리핑과 복습 관리 진입점 | 0 | 대시보드에서 실제 복습·학습으로 이동 |
| 2 | 개념별 근거와 학습 이슈 | 0, 화면 연결은 1 | 오답·설명 결과가 이슈에 누적 |
| 3 | 설명 개선: 학습 PR | 2 | 원본 설명·수정본·재평가 비교 |
| 4 | 영속 실행과 자동 복습 | 2, 3의 평가 연결 | 서버 재시작 후에도 복습 작업 복구 |
| 5 | 학습 메이트 공용 패널 | 1~3, 생성 작업은 4 | 화면 문맥을 따르는 학습 보조 |
| 6 | 학습 준비 자동화 | 4, 기존 요약 식별 체계 | 자료 업로드 후 생성 초안·적용·실패 복구 |
| 7 | 장기 학습 메모리 | 2~4의 수행 이력 | 근거와 정책이 설명되는 개념별 학습 상태 |
| 8 | 외부 서비스 연동 | 4, 내부 일정 ID·설정 | 한 서비스의 연결·가져오기·해제 |

각 단계에서는 API·저장 계약 → DB 권한·원자성 → 서버 → 화면 → 검증 순서로 진행한다. 모든 테이블을 처음부터 만들지 않는다. 1차 공개는 0~3과 해당 통합 검증까지, 자동 복습 공개는 4 완료 후로 나눈다.

## 4. 단계 0 — 기준선과 공통 계약

목표: 진행 중인 구현을 보존하고 새 기능이 같은 ID·상태·저장 규칙을 사용하게 한다.

1. 현재 브랜치·미커밋 변경·마이그레이션 목록을 기록한다. 기존 변경을 되돌리거나 완료 여부를 추정하지 않는다.
2. 현재 테스트를 기준선으로 실행하고, 실패가 있으면 기존 실패와 신규 실패를 구분한다. 저장소 SQL과 실제 배포 DB 버전은 따로 확인한다.
3. 메뉴는 오답 노트 → 복습 관리로 변경하되 /review를 유지한다. 탭은 today/issues/wrong, 상세는 issueId와 안정적인 학습 ID로 복원한다.
4. 학습 경로는 /learn/:sessionId, 복습은 기존 /learn/review/:cardId를 유지한다. 이름이 겹치는 정적·동적 경로를 실제 라우터에서 검사한다.
5. course_id는 UUID, material_id는 기존 TEXT, 자료 참조는 (course_id, material_id, user_id), 근거는 source_hash·unit_id를 사용한다. 화면 표시용 과목명으로 새 관계를 저장하지 않는다.
6. LearningContext 계약을 정한다: route, courseId, materialId, sourceHash, sourceRefs, sessionId, itemId, conceptId, issueId, phase, helpPolicy. 비공개 정답·채점 기준은 포함하지 않는다.
7. 사용자 timezone과 오늘의 경계를 정한다. 기본 Asia/Seoul, DB 시간은 UTC. 날짜만 있는 일정과 시각이 있는 일정을 구분한다.
8. 저장 계약을 정한다: 상태를 변경하는 요청은 명령 키·현재 버전으로 중복과 충돌을 제어한다. 신규 학습 결과는 서버가 소유권과 상태를 확인하고 저장한다.
9. 새 컴포넌트는 기능 폴더에 분리한다. 기존 Summary.tsx·Dashboard.tsx 전체 재작성은 선행 조건으로 삼지 않는다.

주요 대상: App.tsx, common.tsx, CourseContext.tsx의 ID 조회 어댑터, learningSession/navigation.ts, backend.ts, server/auth.py, 기존 세션 공개 응답 모델.

완료 기준: 기존 URL·과목 선택·로그인·초안 복원 동작을 유지하고, 새 데이터의 ID·상태·소유권·시간 계약을 문서와 타입으로 확인할 수 있다.

## 5. 단계 1 — 브리핑과 복습 관리 진입점

화면 위치: 대시보드 상단의 공부 시작하기 카드, /review의 오늘 복습 탭.

1. 공부 시작하기를 오늘의 학습 브리핑으로 확장한다. 진행 중 세션은 이어서 하기 행으로 묶고, 오늘 할 활동은 최대 3~4개만 표시한다.
2. 기존 브리핑 항목에 id, kind, reason, priority, action을 추가한다. action은 허용된 학습 대상 ID를 사용하고 임의 외부 URL을 받지 않는다.
3. 1차 입력은 기존 D-day·진도·점수·계획, 세션 목록, 기존 /reviews의 기한 도래 목록이다. 이슈 추천은 2단계 완료 후 추가한다.
4. 임박한 마감·기한이 지난 복습·이어갈 학습·취약 근거를 정책으로 정렬한다. 같은 활동을 세션·복습·계획이 각각 중복 추천하지 않도록 대상 ID로 합친다.
5. 복습 관리에 오늘 복습과 기존 오답 문항 탭을 넣는다. 이슈 탭은 2단계에서 실제 기능과 함께 공개한다.
6. 복습 시작은 기존 /learn/review/:cardId로 연결한다. 예정일 전 연습은 기존 복습 일정을 앞당긴 성공으로 집계하지 않는다.
7. 복습·세션 조회 실패가 전체 대시보드를 막지 않게 한다. 비어 있음과 불러오기 실패를 별도로 표시한다.
8. 변경 후에는 브리핑·복습 목록을 다시 조회한다. 이후 공통 무효화 이벤트로 확장하며, 화면마다 별도 복습 데이터를 저장하지 않는다.
9. 정확한 총개수는 페이지에 받은 30개 목록 길이로 계산하지 않는다. 필요할 때 소유자 범위의 count/summary 조회를 추가한다.

수정: Dashboard.tsx, briefing.ts, ReviewNotes.tsx, reviews.ts, LearningResume.tsx, common.tsx, 튜토리얼의 메뉴 설명.

신규 제안: LearningBriefing, ReviewHome, TodayReviews, WrongQuestionList 컴포넌트. 첫 단계의 단순 목록 연결 때문에 별도 브리핑 저장 테이블은 만들지 않는다.

완료 기준: 브리핑 → 지정된 복습 → 제출·확인 → 복습 목록 갱신이 가능하다. 새로고침·뒤로 가기·모바일에서도 선택 탭과 대상이 복원된다.

검증: 추천 정렬·중복 제거, 대상 삭제, 과목명 변경, 빈 목록, 부분 조회 실패, 완료 후 갱신.

## 6. 단계 2 — 개념별 근거와 학습 이슈 트래커

화면 위치: 복습 관리의 학습 이슈 탭. 학습 결과·오답 문항에서 이슈 상세로 진입한다.

1. 기존 learning_concepts와 learning_item_concepts를 재사용한다. 동일 원문 버전 안의 연결을 먼저 지원하고, 다른 자료·버전의 동명 개념을 자동 병합하지 않는다.
2. 새 퀴즈에는 안정적인 question_id와 question_version을 부여한다. 기존 퀴즈는 저장된 세트·문항 위치·본문 스냅샷에 연결한 레거시 식별자를 쓰고, 문항 텍스트 일치만으로 병합하지 않는다.
3. 퀴즈-개념 연결은 근거·확정 여부를 저장한다. 예전 weak_topics 문자열은 후보로만 사용한다. 연결이 없는 문항도 기존 오답 보기에서 계속 확인할 수 있다.
4. learning_evidence를 추가한다. 개념, 원본 시도/문항, 수행 종류, 결과, 도움·사전 노출·반복 여부, 원문 버전, 품질 상태, 발생 시각, 정책 버전을 기록한다.
5. learning_issues와 learning_issue_events를 추가한다. 이슈에는 개념·요약·현재 상태·revision을, 이벤트에는 생성·보완 시작·재평가·해결·재발 및 근거를 남긴다.
6. 상태는 확인 필요 → 보완 중 → 재평가 대기 → 해결, 필요 시 다시 열림으로 정한다. AI 오류·평가 불확실·문항 신고는 확정 오답과 분리한다.
7. 새 답안 저장·평가 완료와 evidence/outbox 기록을 같은 DB 트랜잭션에서 처리한다. 기존 브라우저 퀴즈 저장은 원자적 RPC로 점진적으로 옮긴다. 브라우저에서 계산된 정오답은 legacy_client로 구분하고 강한 숙련 근거로 자동 승격하지 않는다.
8. 서버가 실제 기록에서 근거를 생성한다. 사용자가 보낸 concept_id·정오답·점수를 그대로 신뢰해 확정 이슈를 만들지 않는다. 사용자 오답 원인 선택은 별도 자기 보고로 저장한다.
9. 이슈 상세에는 관련 원문, 처음 답변, 피드백, 최근 보완·재평가, 다음 행동을 배치한다. 같은 개념의 재실패는 새 이슈를 무한 생성하지 않고 기존 열린 이슈에 근거를 추가한다.
10. 보완 완료와 해결 판정을 구분한다. 설명을 읽거나 수정했다고 해결하지 않고, 정책이 요구하는 독립 재평가 결과로 전환한다. 사용자가 닫은 이슈는 수동 종료로 구분한다.
11. 기존 기록 이관은 재실행 가능한 배치로 수행한다. 원본 이벤트 ID의 고유 제약으로 중복 생성하지 않는다. 근거가 부족한 과거 기록은 미분류 상태를 유지한다.

DB 제안: learning_evidence, learning_issues, learning_issue_events, question_concept_links, learning_event_outbox. 자료·개념·사용자 삭제 관계와 조회 인덱스, 서버 전용 쓰기 권한을 함께 추가한다.

API 제안: GET /learning-issues, GET /learning-issues/{id}, POST /learning-issues, POST /learning-issues/{id}/actions. 생성은 소유한 학습 item/attempt 또는 수동 메모를 입력받고 근거 유형을 구분한다.

수정: Quiz.tsx, quizAttempts.ts, quizSets.ts, gpt.ts, ReviewNotes.tsx, LearningResults.tsx, learning_sessions의 공개 응답·저장 RPC. 서버는 learning_issues 패키지로 라우터·서비스·저장을 분리한다.

완료 기준: 같은 개념을 두 번 어려워하면 이슈 한 건의 근거가 늘고, 보완·재평가·재발 이력이 보인다. 다른 사용자 기록을 참조할 수 없으며, 중복 제출로 근거·이슈가 늘지 않는다.

## 7. 단계 3 — 설명 개선: 학습 PR

화면 위치: 완료 학습의 개념별 설명 다듬기 버튼, 이슈 상세의 설명 개선하기 버튼. 사용자 명칭은 설명 개선으로 둔다.

1. 학습 결과 DTO에 item_id, concept_id, 기준 attempt_id를 추가한다. 답안·채점 기준 전체를 목록에 실어 보내지 않는다.
2. /learn/:sessionId/revisions/:revisionId 경로를 제안한다. 새 초안을 만들 때 서버가 revisionId를 발급하고, 원본 세션의 항목·시도·원문 버전에 고정한다.
3. explanation_revisions에 기준 답안, 부모 수정본, 수정 답안, 상태, 도움 이력, 원문 버전, draft_revision을 저장한다. 평가 결과는 별도 explanation_evaluations로 누적한다.
4. 화면은 원본 설명 / 수정 설명 / 평가 피드백의 세 영역으로 구성한다. 모바일에서는 세로로 쌓고 변경 내용은 문장·문단 단위로 표시한다.
5. 초안 자동 저장·한글 조합 입력·저장 중 이동·새로고침·다른 탭 충돌을 처리한다. 제출 시 같은 명령 키로 응답 유실을 복구한다.
6. 제출한 답안은 고정한다. 재수정은 새 버전을 만들고, 같은 답안의 모델 오류 재시도와 다른 답안의 새 평가를 구분한다. 기존 세션 attempt를 덮어쓰지 않는다.
7. 기존 Generator.evaluate와 원문 검증을 재사용한다. 변경점 설명을 위해 추가 모델 호출을 기본으로 넣지 않고, 평가 기준별 before/after를 비교한다.
8. 자료·힌트·모범 설명을 참고해 수정한 결과는 보완 후 수행으로 저장한다. 개선 성공만으로 기억 유지·독립 이해를 판정하지 않는다.
9. 개선을 마치면 이슈를 재평가 대기로 바꾸고 별도의 힌트 없는 재평가를 연결한다. 기존 ReviewPractice의 답변 비교와 역할을 구분해 연습 이력은 그대로 보존한다.

API 제안: POST /explanation-revisions, GET /explanation-revisions/{id}, PATCH /explanation-revisions/{id}/draft, POST /explanation-revisions/{id}/submit, GET /explanation-revisions/{id}/evaluations.

수정·재사용: LearningResults.tsx, LearningHistory.tsx, learningSessions.ts, navigation.ts, App.tsx, server/learning_sessions/generation.py. 새 프론트는 explanationRevision 기능 폴더, 서버는 explanation_revisions 패키지로 분리한다.

완료 기준: 원본 답변을 유지하면서 수정본을 저장·평가·비교할 수 있다. 제출 중 새로고침·중복 요청에도 수정본·평가가 중복되지 않고 평가 실패는 미평가로 남는다.

1차 공개 범위: 0~3 완료 후 실제 자료 하나로 브리핑 → 이슈 → 설명 개선 → 재평가 진입까지 검토한다.

## 8. 단계 4 — 영속 실행과 자동 복습 에이전트

화면 위치: 복습 관리의 오늘 복습, 캘린더 복습 표시, 마이페이지 복습 설정.

1. 첫 영속 큐는 기존 Postgres에 background_jobs와 짧은 주기의 별도 워커를 두는 방식으로 시작한다. Redis·새 메시지 인프라는 필수 조건으로 추가하지 않는다.
2. job에는 kind, target_id, input_version, run_after, status, attempts, max_attempts, lease_token, lease_expires_at, idempotency_key, error_code, result_ref를 둔다. 원문·답안 전문은 운영 로그에 남기지 않는다.
3. 학습 결과 저장 트랜잭션에서 기록한 outbox를 워커가 처리한다. 처리 기록·파생 결과·outbox 완료를 원자적으로 반영하고, 재전달 시 같은 근거·복습 카드가 생기지 않게 한다.
4. 작업 획득은 DB 잠금과 lease로 처리한다. 모델 호출은 트랜잭션 밖에서 실행하고, 결과 저장 시 최신 lease·대상 존재·원문 버전·취소 여부를 다시 검사한다.
5. 만료 작업은 재시도 한도·backoff로 복구한다. 문항 오류·권한 없음·자료 삭제는 무한 재시도하지 않는다. 기존 BackgroundTasks와 워커가 같은 평가를 동시에 실행하지 않게 대상별 실행 주체를 전환한다.
6. 학습 완료·이슈 생성·독립 재평가 결과에서 기존 review_cards를 자동 등록·갱신한다. 수동 등록 API는 계속 지원하고 중복 카드를 만들지 않는다.
7. 기존 next_review 정책을 버전화한다. 불확실·미평가·도움 사용·예정일 전 연습은 기존 일정 보호 규칙을 유지한다. 같은 문제 재노출 성공을 새로운 응용 능력으로 표시하지 않는다.
8. 앱 내 복습함을 먼저 제공한다. 기한 도래 자체는 due_at 조회로 판단하고, 날짜가 됐다는 이유만으로 모델을 호출하지 않는다. 앱 종료 중에도 보존되는 일정과 외부 푸시 발송은 별도 기능이다.
9. 미루기·일시 정지·재개를 추가한다. 미루기는 수행 완료가 아니며, 원래 기한·미룬 기한·변경 이유를 기록한다. 사용자 timezone에 맞춰 날짜를 표시한다.
10. 캘린더는 review_cards를 날짜 범위로 조회한다. dashboard_state.plans에 같은 복습을 복사하지 않는다. 계획 항목에 포함할 때는 review_card_id 참조로 연결한다.
11. 기존 자료·문제를 우선 재사용한다. 새 문제 생성은 별도 job으로 다루고 생성 예산·원문 검증·비공개 정답·신고 처리를 적용한다.
12. 워커가 사용할 원문 조회는 서버 전용 소유권 경로로 구현한다. 자동 작업에 만료되는 사용자 JWT를 저장하지 않고, 새 작업 실행 시 소유자·대상·동의 상태를 다시 검사한다.

DB/API 제안: background_jobs, review_schedule_events, review_preferences, outbox 처리 RPC; 기존 /reviews 확장, GET /reviews/summary, POST /reviews/{id}/actions, GET /background-jobs/{id}.

수정: server/reviews.py의 서비스 분리, review_schedule.py, learning_sessions/router.py·service.py의 실행 분리, reviews.ts, Calendar.tsx, MyPage.tsx. 워커 진입점·실행 설정을 별도로 추가한다.

완료 기준: 학습 완료가 복습 카드로 연결되고 대시보드·복습함·캘린더가 같은 상태를 보인다. 서버 종료·워커 재시작·중복 전달·삭제 중 작업이 있어도 복구 가능하며 결과가 한 번만 반영된다. 외부 모델 호출의 과금 정확히 한 번은 보장하지 않는다.

## 9. 단계 5 — 학습 메이트 위젯

화면 위치: 로그인 후 공용 화면 오른쪽 아래. 데스크톱은 측면 패널, 모바일은 하단 패널.

1. AppShell의 CourseProvider 안에 LearningContextProvider와 LearningMateHost를 둔다. 라우트 이동 시 패널은 유지하되 사용자 변경·로그아웃 시 대화·문맥·진행 요청을 초기화한다.
2. AITutorDrawer의 메시지 렌더·첨부·입력·전송·대화 저장을 재사용 가능한 ChatPanel로 분리한다. 자료 상세의 기존 embedded 레이아웃도 같은 핵심 컴포넌트를 사용한다.
3. 각 화면은 현재 자료·선택 구절·이슈·학습 단계만 등록하고, 떠날 때 해제한다. 패널 상단에 현재 연결 자료를 표시한다.
4. 자료·과목·평가 단계가 바뀌면 문맥 버전을 올린다. 이전 문맥의 늦은 응답을 새 자료 답변으로 붙이지 않으며, 범위가 달라진 대화는 별도로 분리한다.
5. /agent가 자료 ID·버전을 받고 서버에서 소유권·원문을 확인하는 경로를 추가한다. 신규 메이트는 브라우저가 보낸 원문을 접근 권한의 근거로 사용하지 않는다.
6. 원문 검색은 현재 자료의 기존 source_scope 단위·제목·용어부터 시작한다. 짧은 근거 목록과 실제 위치를 반환한다. 전체 자료 색인·의미 검색은 별도 후속 범위다.
7. recall/check 답안 작성·시험형 퀴즈 중에는 도메인 답변과 검색을 서버에서도 제한한다. 도움은 기존 학습 help 경로로 제공하고 노출 이력을 저장한다. 일반 /agent 경로가 제한을 우회하지 않도록 활성 평가 문맥도 검사한다.
8. 첫 버전 액션은 이슈 보기·자료 열기·복습 시작 같은 이동이다. 데이터 변경·생성은 해당 기능의 검증된 API와 사용자 실행으로 연결한다.
9. 화면 이동 액션은 LearningNavigationContext의 저장·이탈 검사를 거친다. 공용 채팅이 작성 중 답변을 잃게 하지 않는다.
10. 모바일 입력창·키보드·하단 버튼이 겹치지 않게 하고, 패널 숨기기·키보드 탐색·포커스 복원을 구현한다.

수정: App.tsx, AITutorDrawer.tsx, Summary.tsx, agent.ts, summaryChats.ts, server/agent.py, server/schemas.py, learningSession/navigation.ts.

저장: 자료 기반 대화는 기존 테이블 활용. 자료 없는 일반 학습 대화가 필요하면 별도 target_kind와 전용 저장 계약을 추가하고, 기존 summary_id/material_id 제약을 무작정 제거하지 않는다.

완료 기준: 화면 이동 후 연결 자료가 맞고, 같은 자료에서는 대화를 이어갈 수 있다. 평가 중 정답 제한·도움 기록·초안 보호·로그아웃 초기화가 동작한다.

## 10. 단계 6 — 학습 준비 자동화

화면 위치: 업로드 마지막 단계의 학습 자료도 준비하기 옵션, 자료 상세 상단의 준비 상태, 준비된 초안 보기.

1. 사용자는 요약·퀴즈·설명 학습 준비 중 필요한 작업을 고른다. 자료 저장·변환 성공 이후에만 준비 job을 등록한다.
2. preparation_requests에 대상 자료·원문 해시·범위·옵션·실행 정책을 저장한다. preparation_artifacts에는 결과 종류·초안·검증 상태·적용 대상·generation_id를 저장한다.
3. 변환 → 요약/퀴즈/pack 준비의 의존 관계를 표현한다. 생성 task끼리는 독립 실패를 허용하고, 원문 변환 실패 후 후속 생성을 시작하지 않는다.
4. 요약은 기존 summary request_key·source_hash·generation_id를 재사용한다. 작업 재시도와 사용자가 누른 새로 생성은 서로 다른 명령으로 구분한다.
5. 퀴즈는 유형·문항 수·정답 범위·원문 근거를 검사한다. 학습 pack은 기존 prepare 생성·검증을 재사용하고 사용자 학습 세션은 시작 버튼을 눌렀을 때 만든다.
6. 초안 검토 화면에서 결과를 확인·재생성·폐기·적용한다. 적용은 기존 summaries·quiz_sets·pack 저장소를 대상으로 하며, 적용된 ID와 generation_id를 남긴다.
7. 중복 적용은 같은 결과를 반환한다. 기존 요약·퀴즈를 덮어쓰지 않고 새 결과나 명시된 버전으로 저장한다. 여러 결과의 적용은 개별 상태로 보여준다.
8. 원문이 바뀌면 이전 작업 결과를 구버전 초안으로 표시하고 현재 자료에 자동 적용하지 않는다. 삭제·취소한 작업의 늦은 응답도 적용하지 않는다.
9. 작업별 재시도·취소, 사용자별 동시 생성·호출량 제한을 추가한다. 모델 사용량은 기존 metrics를 재사용해 기능·작업별로 연결한다.
10. 업로드 탭을 닫았다가 다시 열어도 자료 ID로 준비 상태를 복원한다. 초안 내용은 브리핑에 넣지 않고 준비 완료·확인 필요 정도만 표시한다.

API 제안: POST /preparation-requests, GET /preparation-requests/{id}, POST /preparation-requests/{id}/actions, GET /preparation-artifacts/{id}, POST /preparation-artifacts/{id}/apply.

수정: Summary.tsx 업로드·상세, summaryGeneration.ts·summaries.ts, quizSets.ts, server/main.py 생성 함수 분리. 신규 PreparationOptions, PreparationStatus, PreparationDraftView 및 preparation 서버 패키지.

완료 기준: 파일 업로드 → 생성 예약 → 화면 종료 → 재접속 → 초안 확인 → 한 번 적용이 가능하다. 부분 실패·중복 요청·원문 변경·서버 재시작 후에도 작업 상태와 기존 결과가 보존된다.

## 11. 단계 7 — 장기 학습 메모리

화면 위치: 학습 통계의 개념별 학습 기록 탭, 개념 상세. 브리핑 추천의 입력으로도 사용한다.

1. 2~4단계의 learning_evidence와 review_attempts를 원본으로 유지한다. 별도의 LLM 대화 요약을 확정 학습 능력으로 저장하지 않는다.
2. concept_learning_state에 최근 결과·다른 문항 수·독립/도움 사용 수행·지연 평가·마지막 평가·다음 복습·정책 버전을 저장한다. 파생 상태는 원본으로 재계산할 수 있어야 한다.
3. 미평가·확인 필요·보완 필요·재평가 대기·최근 안정으로 표시한다. 자기 점검·미평가·신고·예정일 전 반복 결과의 반영 규칙을 분리한다.
4. 한 번의 정답이나 같은 문항 반복만으로 안정 판정을 올리지 않는다. 현재 복습의 반복 문항 성공과 별도 문제의 독립 수행을 구분한다.
5. 화면에 최근 상태의 근거와 시점을 표시한다. 점수·시간의 합계는 기존 퀴즈·세션·복습 중복 여부와 방치 시간 한계를 확인한 뒤 집계한다.
6. 개념 상세에 시도·설명 수정·이슈·복습 타임라인과 관련 원문·다음 행동을 표시한다. 정책이 바뀌면 재집계하고 표시 정책 버전을 갱신한다.
7. 자료 버전마다 다른 learning_concepts를 묶는 canonical_concepts와 concept_identity_links는 필요한 시점에 추가한다. 사용자 확인 또는 근거 검토 없이 동명 개념을 합치지 않는다.
8. 선수·관련 관계는 concept_relations로 별도 관리한다. 초기에는 학습 이력 목록과 상세를 먼저 공개하고, 관계 그래프는 유효한 연결이 쌓인 뒤 추가한다.
9. 상태 집계는 이벤트 기반 증분 처리와 누락 복구 재집계를 지원한다. 자료·계정 삭제 시 집계와 추천 캐시도 무효화한다.

API 제안: GET /learning-concepts, GET /learning-concepts/{id}/history, GET /learning-concepts/{id}/state. 개념 병합·관계 편집은 revision을 갖는 별도 명령으로 둔다.

수정: Stats.tsx, learningStats.ts, briefing 입력, 메이트의 허용된 개인 학습 문맥. 신규 ConceptHistory, ConceptTimeline, ConceptStateSummary.

완료 기준: 같은 개념의 설명 개선·독립 재평가·지연 복습을 구분해 볼 수 있다. 상태가 어떤 근거로 바뀌었는지 설명되며 원본 삭제·정책 변경 후 재집계할 수 있다.

## 12. 단계 8 — 외부 서비스 연동

화면 위치: 마이페이지 연결된 서비스 카드, 캘린더 가져온 일정, 연결된 일정의 과목 지정.

첫 범위는 캘린더 한 서비스의 읽기 전용 가져오기로 제안한다. 공급자 API·심사·권한의 실제 요건은 구현 착수 시 공식 문서와 등록 앱 설정을 확인한다.

1. OAuth 연결 시작·콜백·state 검증·일회성 연결 요청·토큰 갱신·해제 계약을 구현한다. 로그인 공급자 연결과 학습 일정 접근 동의를 구분한다.
2. 토큰은 서버 전용 암호화 저장소에 보관한다. 브라우저·공개 profiles·작업 로그에 넣지 않는다. 워커는 connection_id만 참조한다.
3. external_connections, external_event_links, sync_runs를 추가한다. provider와 외부 event_id·반복 인스턴스 ID로 중복을 방지하고 내부 일정 ID와 연결한다.
4. 동기화는 4단계 워커에서 실행한다. 실패·인증 만료·재연결 필요·마지막 성공 시각을 마이페이지에 표시한다.
5. 일정 시간대·종일 일정·반복 일정·외부 수정·삭제를 구분한다. 외부 일정이 바뀌어도 내부 수동 학습 계획을 덮어쓰지 않는다.
6. 가져온 일정에 과목을 직접 연결할 수 있게 한다. 이름 부분 일치로 과목을 확정하지 않는다. 외부 일정은 읽기 전용 표시와 출처를 제공한다.
7. 내부 저장은 학습 계획용 dashboard_state JSON과 별도 external event 모델로 구분한다. 캘린더 화면에서 합쳐 표시하고, 계획 엔진은 외부 일정 ID를 참조한다.
8. 연결 해제는 후속 동기화를 즉시 중단하고 자격 증명을 폐기한다. 가져온 일정·연결 이력을 보존할지 삭제할지 선택하고, 늦게 도착한 동기화가 데이터를 다시 만들지 않게 한다.
9. 양방향 쓰기·Drive 자료 수집·여러 서비스·상시 외부 알림은 후속 범위로 둔다.

API 제안: GET /integrations, POST /integrations/{provider}/connect, 공급자 callback, POST /integrations/{id}/sync, DELETE /integrations/{id}, GET /external-events.

수정: MyPage.tsx, Calendar.tsx, 서버 integrations 패키지, worker 동기화 handler. 운영 자격 증명·등록 앱이 준비되기 전에는 가짜 성공 상태를 제공하지 않는다.

완료 기준: 연결 → 권한 확인 → 가져오기 → 외부 수정 반영 → 과목 연결 → 해제가 한 서비스에서 작동한다. 중복·인증 만료·시간대·외부 삭제를 처리한다.

## 13. 단계 9 — 통합 검증과 공개

개발 단계별 확인을 먼저 끝내고, 실제 변경·실패·미확인 항목이 있을 때 검증 범위를 넓힌다. 계획 문서 작성만으로 구현·운영 적용·모델 품질이 검증됐다고 표시하지 않는다.

| 검증 범위 | 핵심 시나리오 | 확인 방법 |
| --- | --- | --- |
| 기존 기능 | 요약·퀴즈·자료 업로드·학습 저장·재개 유지 | 관련 Vitest·서버 테스트, 필요한 화면 수동 확인 |
| DB 관계·권한 | 사용자 간 접근, 서버 전용 정답, 복합 소유권, 삭제 cascade | test-learning-db 및 실제 Postgres 통합 환경 |
| 명령 중복·동시성 | 응답 유실, 같은 명령 재전송, 서로 다른 탭, 중복 job | API·DB 동시 실행 사례 |
| 상태 복구 | 초안 작성 중 새로고침, 모델 실패, 서버·워커 종료, 만료 lease | 브라우저와 워커 재시작 시나리오 |
| 원문 변경 | 작업 예약 뒤 수정·삭제, 과거 스냅샷 열기 | 고정 fixture와 실제 자료 확인 |
| 학습 의미 | 도움 후 정답, 반복 문항, 예정일 전 연습, 지연 재평가, uncertain | 정책 단위 테스트·내용 검토 |
| 화면 | 좁은 화면, 한글 입력, 키보드·포커스, 긴 자료명 | 브라우저 검증 |
| 외부 연동 | 만료 토큰, 반복·종일 일정, 중복 가져오기, 해제 중 job | 공급자 테스트 계정·고정 응답 |

기본 실행 후보: npm test, npm run lint, npm run build, npm run test:learning-db, server 환경의 python -m pytest -q. 새 워커에는 lease·재전달·중단·지연 응답 테스트를 추가한다. 전체 검증은 해당 배포 묶음의 변경이 모인 시점에 수행한다.

공개 절차:

1. 호환 가능한 새 마이그레이션을 추가하고 초기 schema.sql에도 같은 구조를 반영한다. 기존 번호의 마이그레이션을 재작성하지 않는다.
2. 새 서버·워커가 구형 데이터와 함께 동작하는지 확인한 뒤 새 화면을 공개한다. 신규 생성·자동 등록·동기화를 기능별로 중지할 수 있게 한다.
3. 기능을 끌 때는 새 작업 등록을 막고, 이미 저장된 답변·이력 조회는 유지한다. 진행 중 job은 안전한 종료 또는 취소 규칙을 따른다.
4. 실제 자료 소수로 질문·원문 근거·평가·복습 일정을 검토한다. 구조 테스트와 학습 내용 품질 검토 결과를 따로 기록한다.
5. 완료한 묶음만 공개하고, 공개하지 않은 기능은 비활성 메뉴 대신 화면에서 숨긴다.

## 14. 공통 데이터·상태 계약

| 도메인 | 기준 데이터 | 함께 복사하지 않을 데이터 |
| --- | --- | --- |
| 원본 수행 | learning_session_attempts, quiz_attempts, review_attempts | 원본 답안을 새 이슈 본문으로 무제한 복제하지 않음 |
| 진단 근거 | learning_evidence | 브라우저가 보낸 임의 점수를 확정 능력으로 사용하지 않음 |
| 이슈 | learning_issues + events | 오답 분석 최신 한 건을 이슈 이력으로 대체하지 않음 |
| 복습 일정 | review_cards + schedule_events | dashboard_state.plans에 별도 복습 사본을 만들지 않음 |
| 설명 개선 | explanation_revisions + evaluations | 기존 제출 attempt를 수정본으로 덮어쓰지 않음 |
| 자동 실행 | background_jobs + outbox | 화면 열림·브라우저 타이머에 실행을 의존하지 않음 |
| 생성 초안 | preparation_requests + artifacts | 승인 전 결과를 기존 공개 요약·퀴즈에 덮어쓰지 않음 |
| 장기 상태 | concept_learning_state | 파생 상태를 원본 근거 대신 영구적인 진실로 취급하지 않음 |
| 외부 일정 | external_connections + event_links | 외부 변경을 내부 수동 일정에 덮어쓰지 않음 |

모든 상태 변경은 현재 버전·소유권·허용된 행동을 서버가 검사한다. 이벤트 payload는 schema_version을 갖고, 원본 변경과 outbox 기록을 한 트랜잭션에서 저장한다. 파생 처리는 최소 한 번 전달을 전제로 중복을 제거한다.

공용 오류는 인증 필요·대상 없음·상태 충돌·원문 변경·처리 중·입력 오류·일시 실패를 구분한다. 목록은 cursor/limit을 지원하고 원문·답안·정답 전문은 상세 공개 규칙에 따라 반환한다.

계정·자료 삭제는 파생 이슈·복습·초안·job·집계·검색 캐시까지 반영한다. 서버 기록 삭제와 별도로 학습·복습·설명 개선 로컬 초안을 사용자별로 정리한다. 신규 기능은 현재 clearLearningDrafts만으로 전부 정리된다고 가정하지 않는다.

## 15. 규모 추정과 권장 배포 묶음

아래는 단일 개발자가 전담하고 현재 코드가 재사용 가능하다는 가정의 계획용 인일이다. 일정 약속이 아니며, 0단계 검증 후 다시 산정한다. 운영 DB 조사·기존 실패 수정·OAuth 심사 대기·외부 의존 대기는 별도다.

| 단계 | 추정 인일 | 주요 변동 요인 |
| --- | --- | --- |
| 0 | 1~2 | 현재 미커밋 구현·마이그레이션·기존 실패 |
| 1 | 2~3 | 대시보드·리뷰 화면 연결·복원 |
| 2 | 5~7 | 기존 퀴즈 식별·근거 신뢰도·이관 |
| 3 | 4~6 | 수정본 모델·초안·평가 비교 |
| 4 | 6~9 | 워커·원자성·중단 복구·자동 등록 |
| 5 | 4~6 | 기존 채팅 분리·문맥·평가 중 제한 |
| 6 | 5~8 | 생성 함수 분리·초안 적용·재사용 |
| 7 | 5~8 | 상태 정책·기존 데이터 품질·개념 연결 |
| 8 | 5~8 | 공급자 권한·동기화·일정 저장 |
| 9 | 3~5 | 통합·내용 품질·실패 수정 |
| 합계 | 40~62 | 순차 전담 기준 약 8~13주, 외부 대기 제외 |

권장 묶음은 A: 0~3의 추천·이슈·설명 개선, B: 4의 자동 복습, C: 5~6의 메이트·준비 자동화, D: 7~8의 장기 이력·외부 연동이다. 9단계 검증을 각 공개 묶음에 배분한다. 일정이 줄어들면 이슈 기록과 복습 실행의 연결을 먼저 완성하고 고급 그래프·신규 문제 자동 생성·다중 외부 서비스를 후순위로 둔다.

## 16. 단계별 완료 기록 템플릿

각 구현 묶음은 다음 내용을 남긴 뒤 다음 단계로 넘어간다.

- 사용자에게 달라진 화면·행동과 실제 진입 URL.
- 재사용한 기존 구현, 추가한 API·마이그레이션·기능 플래그.
- 실행한 검증과 결과, 실제 DB·모델·외부 서비스에서 미확인인 항목.
- 남은 오류·다음 단계의 의존 관계, 기능 중단 시 보존되는 데이터.

본 문서의 모든 단계 상태는 계획이다. 현재 기능의 완료 여부는 원래 진행 기록과 실제 코드·검증 결과에서 확인한다.
