# Tongkk 새 학습 기능 추가 계획

작성일: 2026-11-19 / 코드 확인 기준: main, 4488bd5

이 문서는 기존 품질·운영 개선 계획과 별도로 관리한다. 기존 notes/quality-and-operations-plan.md에는 추가하지 않는다. 아래 API·테이블·파일 이름과 정책 수치는 개발 제안이며 현재 구현된 기능이 아니다.

## 1. 목표와 기능 간 연결

이번 새 기능 범위는 다음 세 가지다.

1. 학습 계획 생성 및 최적화: 공부할 활동을 고르고, 날짜별 가용 시간과 마감 안에 배분한다.
2. 관련 원문 구간 검색 기반 튜터: 질문과 연결된 강의자료 구간을 찾고, 확인 가능한 출처를 붙여 설명한다.
3. 취약 개념 분류 고도화: 어떤 개념의 어떤 활동에서 어려움을 보였는지 기록하고, 보완 활동과 재평가를 연결한다.

공통 흐름은 자료 등록 → 원문 구간·개념 연결 → 문제 풀이 → 개념별 상태·오답 원인 확인 → 관련 원문으로 보완 → 학습 계획 배치 → 재평가다.

개념 ID와 원문 위치를 연결점으로 삼는다. 처음부터 전공 전체의 선수지식 그래프나 장기 추천 모델을 만들지는 않는다. 과목 하나·자료 하나에서 이 흐름이 완주하는 것을 첫 완료 기준으로 삼는다.

## 2. 현재 구현과 보완 지점

| 영역 | 현재 코드 | 새 기능에서 필요한 변경 |
| --- | --- | --- |
| 계획 생성 | /study-plan이 LLM으로 활동·시간·day_offset 생성 | 활동 선택·시간 배분·제약 검사를 서버의 일반 코드로 이동 |
| 계획 제약 | 프롬프트가 여러 날 전체 항목 합계에 daily_minutes를 적용, 서버는 항목 형식 위주로 검사 | 날짜별 가용 시간과 마감을 실제 계산·검증 |

| 오답 분석 | 과목별 최신 분석 한 건을 덮어씀 | 개념별 근거와 보완·재평가 이력을 누적 |

이전 개선 계획의 채점 일관성·사용량 기록은 연계 대상이다. 모든 개선 작업이 끝나야 착수하는 구조로 만들지는 않는다. 검증이 어려운 채점·출처는 새 진단에서 확인 필요 상태로 제외한다.

## 3. 공통 데이터 기반

### 3.1 원문 구간과 버전

- 자료의 실제 추출 Markdown 해시와 추출·분할 버전으로 원문 버전을 식별한다. 파일명·크기가 같은 자료를 같은 내용으로 단정하지 않는다.
- 페이지/슬라이드 → 제목/섹션 → 문단 순서로 나누고, 긴 섹션만 추가 분할한다.
- 각 구간에 사용자·과목·자료 ID, 원문 버전, 섹션 경로, 페이지 범위, 원문 내 위치, 본문, 추출 방식·불확실성 표시를 저장한다.
- 표·수식·코드의 내부 구조를 가능한 한 보존한다. 크기는 샘플 평가로 정하며 문맥이 끊기면 인접 구간을 함께 제공한다.
- 페이지 마커가 없는 자료는 섹션·문단 위치를 제공한다. 존재하지 않는 PDF 페이지 번호를 만들지 않는다.
- 이미지·OCR·비전 설명은 추출 텍스트와 원본 관찰을 구분한다. 비전 설명을 검증된 원문 인용처럼 표시하지 않는다.
- 자료 변경 시 새 버전을 만들고 색인 완료 후 활성 버전을 교체한다. 삭제·접근 권한 변경은 검색과 대화에서 즉시 반영한다.
- 이전 버전의 텍스트 근거를 보존할 수 있게 원문 텍스트 스냅샷을 저장한다. 과거 PDF 파일 자체가 보존되지 않았다면 텍스트 근거만 열고 과거 PDF로 이동 가능하다고 표시하지 않는다.

### 3.2 개념 목록

- 개념은 사용자·과목 범위의 concept_id, 이름, 별칭, 설명, 연결 원문 구간, 분류 상태로 관리한다.
- 첫 버전은 자료의 제목·용어·수동 태그로 후보를 만든다. AI를 쓰더라도 원문 근거가 있는 후보만 제안하고 검증 후 반영한다.
- 같은 개념의 한글·영문 별칭은 연결하되, 같은 이름의 다른 의미는 자동 병합하지 않는다.
- 문제는 주 개념과 보조 개념을 구분한다. 한 문제를 틀렸다는 이유로 연결된 모든 개념을 동일하게 취약 판정하지 않는다.
- 개념을 수정·병합해도 과거 문항·진단의 근거를 추적할 수 있도록 별칭·병합 이력을 유지한다.

### 3.3 제안 테이블

| 테이블 | 역할 | 주요 필드 |
| --- | --- | --- |
| material_source_versions | 원문 버전·색인 상태 | user_id, course_id, material_id, content_hash, markdown_snapshot, extraction_version, index_status |
| material_chunks | 검색·인용 가능한 구간 | source_version_id, chunk_id, section_path, page_start/end, start/end_offset, text, extraction_type |
| course_concepts | 과목별 개념 목록 | user_id, course_id, concept_id, name, aliases, status |
| concept_source_links | 개념과 원문 근거 연결 | concept_id, chunk_id, relation_type, mapping_status |
| question_concept_links | 문항과 개념·근거 연결 | quiz_set_id, question_id, concept_id, role, source_refs, mapping_version |
| concept_learning_evidence | 정오답·수행 조건·원인 근거 | attempt_id, question_id, concept_id, score, hint_used, confidence, error_cause, cause_status, occurred_at |
| concept_learning_state | 개념별 파생 상태 | concept_id, status, evidence_count, distinct_question_count, last_evaluated_at, next_review_at, policy_version |
| study_preferences | 계획 선호·가용 시간 | user_id, timezone, weekly_minutes, date_overrides, session_preferences |
| study_plan_revisions | 계획 초안·적용 이력 | user_id, revision_id, base_revision, horizon, input_snapshot, policy_version, status |
| study_plan_items | 날짜별 실행 활동 | revision_id, task_key, source_refs, concept_ids, date, minutes, action, status, pinned, reasons |

이 목록은 한 번에 모든 테이블을 만드는 일정이 아니다. 단계별로 필요한 테이블만 추가한다. 원문·개념 테이블부터 시작하고, 기존 quiz_sets·quiz_attempts는 안정적인 question_id와 새 메타데이터를 점진적으로 확장한다.

신규 자료 참조는 materials의 실제 복합 키(course_id, id)를 반영한다. 모든 조회·수정·검색은 인증 사용자 소유 관계를 확인한다. user_id 컬럼만 검사하면서 다른 사용자의 course/material ID를 참조할 수 없게 제약·RLS를 함께 설계한다.

## 4. 새 기능 A — 관련 원문 구간 검색 기반 튜터

### 4.1 사용자 흐름

1. 현재 자료 또는 사용자가 선택한 같은 과목의 자료에서 질문한다.
2. 관련 구간과 자료명·페이지·섹션이 먼저 표시된다.
3. 추가 설명이 필요하면 검색 근거를 이용해 튜터가 답한다.
4. 답변의 출처를 누르면 해당 원문 위치가 열린다.
5. 해결하지 못한 질문은 해당 개념의 확인 필요 항목으로 남길 수 있다. 질문했다는 사실만으로 취약 판정하지 않는다.

원문 찾기는 LLM 없이 제공한다. 기존 채팅은 서버가 질문마다 관련 원문을 먼저 검색하고 그 결과를 설명에 사용하는 방식으로 유지할 수 있다.

### 4.2 검색 구현

1. 초기 검색 범위는 현재 선택 자료다. 과목 전체 검색은 사용자 선택으로 넓힌다.
2. 한국어·영문 용어, 개념 별칭, 코드 식별자·수식 기호를 고려해 질의를 정규화한다. 수식·코드의 의미 있는 기호를 일괄 제거하지 않는다.
3. 1차는 제한된 자료 범위의 정확 용어·별칭·제목·본문 키워드 검색으로 후보를 만든다. 제목·용어 일치와 선택 문맥을 우선한다. 실제 SQL 검색 방식과 인덱스는 한국어·코드 질의 샘플로 확인한다.
4. 비슷한 인접 결과를 묶고, 서로 다른 근거가 포함되도록 중복을 줄인다. 상위 결과 수와 본문 총량에 상한을 둔다. 초기 Top-5는 조정 가능한 시작값이다.
5. 표·코드가 중간에 끊기면 같은 섹션의 인접 구간을 확장한다. 확장 후에도 근거 범위 상한을 지킨다.
6. 키워드로 놓치는 질문은 평가셋에 모은다. 임베딩·의미 검색은 검색 누락과 비용을 비교한 뒤 2차로 추가한다.
7. 근거가 약하거나 없으면 검색 범위 변경·질문 구체화를 안내한다. 관련 없는 구간을 정답 근거처럼 채우지 않는다.
8. 캐시는 사용자·자료 접근 범위·활성 원문 버전·질의·검색 버전으로 구분하고, 자료 변경·삭제 시 무효화한다.

### 4.3 API·튜터 연결

- POST /tutor/retrieve: 과목·자료 범위, 질문, 선택 구절을 받아 서버가 접근 가능한 원문 구간을 반환. query, hits, retrieval_status, source_version을 제공한다.
- /agent 확장: 원문 전체 전송 대신 자료 ID·원문 버전·허용 범위·대화 ID를 전달한다. 서버가 매 턴 범위를 검증하고 검색한다.
- search_original_source 도구: 서버가 주입한 사용자·허용 자료 범위에서만 검색한다. 모델이 user_id나 임의 자료 범위를 지정하지 못하게 한다.
- 대명사 중심 후속 질문은 직전 질문·개념·선택 구절을 검색 문맥에 사용하되 전체 대화를 무제한 붙이지 않는다.
- 대화의 자료 범위가 바뀌면 새 대화로 전환하거나 서버 상태를 명시적으로 갱신한다. 이전 원문이 메모리에 남아 다른 자료의 근거로 사용되지 않게 한다.
- 답변은 본문과 구조화된 citations를 분리한다. chunk_id·버전·페이지·인용 범위가 실제 검색 결과에 포함되는지 검사한다.
- 인용 위치가 유효하다는 것과 문장이 사실이라는 것은 별도로 평가한다. 의미가 원문에 의해 지지되는지는 고정 평가 사례와 사람 검토로 확인한다.
- 대화 메시지에 출처 메타데이터를 저장해 재접속 후에도 근거를 복원한다. 삭제된 자료는 접근 불가 상태를 표시한다.

### 4.4 수정 파일과 완료 기준

- 신규 서버: source_index.py, source_search.py와 관련 라우터·스키마·테스트.
- 수정 서버: server/main.py, server/agent.py, server/schemas.py.
- 신규 프론트: sourceSearch 서비스, SourceEvidenceList, SourceCitation 컴포넌트.
- 수정 프론트: src/services/agent.ts, src/services/summaryChats.ts, src/components/AITutorDrawer.tsx, 자료 상세·PdfViewer 연결.
- DB: 원문 버전·구간, 출처 메타데이터, 관련 권한 정책.

완료 기준: 질문 30개 수준의 초안 평가셋에서 정답 근거가 검색 결과에 포함되는지, 무관 질문에서 근거 없음을 반환하는지, 출처 클릭·다중 자료·삭제·사용자 간 격리가 작동하는지 확인한다. 검색 정밀도·근거 포함률·지연·답변 입력량을 기존 전체 원문 전달 방식과 비교한다. 수치 목표는 기준선 측정 후 확정한다.

## 5. 새 기능 B — 취약 개념 분류 고도화

### 5.1 구분해야 할 정보

| 구분 | 예시 | 사용처 |
| --- | --- | --- |
| 개념 | 이진 탐색, 행렬 곱 순서 | 무엇을 다시 공부할지 |
| 수행 종류 | 정의 설명, 기초 적용, 응용, 지연 재평가 | 어떤 방식으로 확인할지 |
| 오답 원인 | 개념 부족, 선수지식 부족, 계산 실수, 조건 해석, 기억 실패, 미확인 | 어떤 보완 활동을 할지 |
| 수행 조건 | 힌트 사용, 정답 열람, 같은 문항 반복, 학생 확신도 | 결과를 얼마나 강한 근거로 볼지 |

정답률만으로 오답 원인을 확정하지 않는다. 객관식 선택지만 있는 경우에는 계산 실수·기억 실패 등을 구분할 수 없어 원인 미확인으로 남길 수 있다.

### 5.2 구현 작업

1. 자료별 개념 후보와 근거 구간을 만들고 중복·별칭을 정리한다. 학생이 개념 이름·연결을 수정할 수 있게 한다.
2. 신규 문제에 안정적인 question_id, 주/보조 concept_id, 원문 근거를 연결한다. AI가 제안한 ID는 같은 사용자·과목의 실제 개념인지 검사한다.
3. 기존 문제는 제목·해설·원문 연결로 후보를 만들되 확실하지 않은 연결은 확인 필요로 남긴다. 과거 weak_topics 문자열을 확정 개념으로 자동 변환하지 않는다.
4. 문항별 정오답·점수·시간·힌트·정답 열람·반복 여부를 기록한다. 선택적으로 답변 전 확신도(확실/애매/모름)를 받는다.
5. 오답 직후 원인 선택 UI를 제공한다. 풀이가 있으면 AI가 원인 후보와 근거를 제안할 수 있지만 사용자 확인·근거 유무를 별도로 저장한다.
6. 기존 과목별 최신 분석은 요약 화면으로 유지할 수 있으나, 새 개념 진단의 근거는 개별 evidence로 누적한다.
7. 개념 상태는 일반 코드로 집계하고 정책 버전을 기록한다. 반복 평가·다른 문항·최근 결과·힌트 유무를 분리해 보여준다.
8. 같은 문항을 짧은 시간에 반복한 결과가 개념 이해를 과하게 끌어올리지 않도록 동일 문항·세션의 반영량을 제한한다.
9. 불확실한 OCR, 오류 신고 문항, 채점 모순은 pending_quality로 분리하고 확정 진단에 반영하지 않는다. 문항이 수정되면 관련 상태를 재집계한다.
10. 보완 활동을 완료해도 바로 이해 완료로 바꾸지 않는다. 별도의 힌트 없는 재평가 결과로 상태를 갱신한다.

### 5.3 개념 상태 정책 초안

| 상태 | 의미 | 추천 행동 |
| --- | --- | --- |
| 미평가 | 연결 개념은 있으나 수행 근거 없음 | 짧은 진단 문제 |
| 확인 필요 | 한 번 틀림·근거 적음·확신도 불일치 | 추가 문항으로 확인 |
| 보완 필요 | 서로 다른 문항·시점에서 반복된 어려움 | 원인에 맞는 보완과 원문 확인 |
| 재평가 대기 | 보완 활동은 했으나 독립 수행 확인 전 | 다른 문항·날짜의 확인 문제 |
| 최근 안정 | 충분한 독립 수행·지연 재평가 근거 있음 | 복습 기한에 맞춰 유지 확인 |

횟수·가중치·점수 임계값은 정책 설정으로 관리한다. 초기에는 서로 다른 문항·세션 수를 명시하고 보수적으로 판정한다. 읽지 않은 개념을 취약으로, 한 번 맞힌 개념을 완전 이해로 표시하지 않는다. 과목 난이도나 문항 난이도가 다른 점수를 그대로 같은 의미로 합산하지 않는다.

### 5.4 원인별 보완 활동

| 원인 | 추천 활동 | 확인 방식 |
| --- | --- | --- |
| 개념 부족 | 관련 정의·비교 원문 확인, 튜터의 단계별 설명 | 표현이 다른 기초 문제 |
| 선수지식 부족 | 확인된 관련 기초 개념으로 이동 | 기초 개념 진단 후 원래 문제 |
| 계산 실수 | 계산 과정 점검·예제 대조 | 같은 원리의 다른 수치 문제 |
| 조건 해석 | 조건 표시·비교 설명 | 조건을 바꾼 문제 |
| 기억 실패 | 짧은 회상·간격 복습 | 시간이 지난 뒤 힌트 없는 문제 |
| 원인 미확인 | 추가 질문·풀이 입력·사용자 선택 | 근거를 모은 뒤 다시 분류 |

새 문제 생성이나 추가 AI 설명은 별도 요청으로 수행한다. 계획을 만들었다는 이유만으로 문제·설명 생성을 자동 연쇄 호출하지 않는다. 선수지식 관계가 없으면 관련 관계를 만들어 확정하지 않고 후보로 남긴다.

### 5.5 UI·API·완료 기준

- 개념별로 근거 문항 수·최근 결과·수행 조건·원인·다음 행동을 보여준다.
- 원문 보기, 튜터에게 묻기, 다시 풀기, 학습 계획에 넣기를 연결한다.
- 기존 오답 노트는 문제별 보기를 유지하고 개념별 보기를 추가한다.
- API 제안: GET /concepts, GET /learning/weaknesses, POST /learning/evidence, PATCH /learning/evidence/{id}/cause.
- evidence는 소유한 실제 문항·시도에서 파생한다. 임의로 보낸 정오답 문자열을 무조건 확정 근거로 저장하지 않는다. 사용자 원인 선택은 진단 근거와 구분한다.
- 수정 대상: Quiz.tsx, ReviewNotes.tsx, Stats.tsx, gpt.ts의 문제 타입, quizSets.ts, quizAttempts.ts, wrongAnswerAnalyses.ts, 서버 퀴즈 스키마·검증·새 개념 집계 모듈.

완료 기준: 한 문제 오답·힌트 후 정답·같은 문제 반복·다른 문제 성공·지연 재평가·오류 문항의 사례에서 상태가 설명 가능하게 바뀐다. 원인 분류의 사람 검토 일치도와 미확정 비율을 함께 측정한다. 근거가 없는 원인 단정을 줄이는 것이 1차 목표다.

## 6. 새 기능 C — 학습 계획 생성 및 최적화

### 6.1 역할 분리

활동 선택·날짜·시간·제약·재배치는 일반 코드가 담당한다. LLM은 필요할 때 자유로운 과제 설명을 활동 초안으로 나누거나 문구를 다듬는 선택 기능으로 둔다. 선택 기능이 실패해도 기본 계획이 만들어져야 한다.

1차 계획 엔진은 규칙 기반 우선순위와 제약을 지키는 배치·재조정으로 구현한다. 전체 조합의 수학적 최적해나 학습 성과 개선이 입증됐다고 표현하지 않는다.

### 6.2 입력 정보

| 입력 | 1차 처리 |
| --- | --- |
| 시험·과제 | 안정적인 ID, 과목 ID, 날짜·알려진 시각, 준비 범위·목표 |
| 가용 시간 | 요일별 공부 가능 순시간, 특정 날짜 예외, 0분 휴식일 |
| 학습 범위 | 자료·페이지·퀴즈·사용자가 지정한 분량과 남은 진도 |
| 수행 이력 | 최근 퀴즈·오답, 수행 조건, 개념 상태·진단 확실성 |
| 복습 | next_review_at 또는 복습 시스템의 due_at |
| 기존 계획 | 수동·완료·고정·미완료·진행 중 항목과 잔여량 |
| 선호 | 목표, 익숙함, 세션 길이, 가벼운/기본/집중 모드 |
| 기준 시각 | 서버의 timezone-aware 현재 시각, 사용자 시간대 |

가용 시간은 수업·일상 일정을 제외하고 사용자가 입력한 공부 가능 시간이다. 외부 캘린더를 자동 수집하지 않는다. 같은 수업 시간을 다시 빼는 이중 차감을 피한다.

과목명 부분 일치로 일정을 연결하지 않고 사용자가 과목을 선택하게 한다. 날짜만 있는 시험은 시험 시각을 아는 것처럼 당일 공부를 배치하지 않으며, 기본적으로 전날까지 준비하도록 안내한다.

### 6.3 실행 활동 후보 생성

1. 시험 범위·남은 진도에서 읽기, 기존 퀴즈 확인, 오답 보완 등 실행 가능한 활동을 만든다.
2. 보완 필요 개념은 원인별 활동을 제안하고, 근거가 적은 개념은 긴 보충 학습보다 짧은 진단을 우선한다.
3. due_at이 지난 복습, 미완료 작업의 남은 부분, 과제의 확인·초안·검토 단계를 후보로 만든다.
4. 활동마다 task_key, 과목·개념·원문/문항 참조, 잔여 분량, 예상 시간, 마감, 선후 관계, 분할 가능 여부를 기록한다.
5. 안정적인 task_key와 복습 회차 ID로 중복·재시도를 구분한다. 같은 개념의 다음 복습과 같은 활동의 중복 생성을 혼동하지 않는다.
6. 실제로 열 수 있는 자료·퀴즈·오답에만 실행 링크를 단다. 내용이 없으면 자료 준비·문제 생성 요청을 선행 활동으로 표시한다.
7. 특정 분량·활동 유형별 초기 소요 시간을 설정값으로 두고 추정임을 표시한다. 활동 시간 기록이 쌓이면 개인별 중앙값 등 보수적인 추정으로 보정한다.
8. 현재 quiz_attempts.duration_seconds는 방치 시간을 포함할 수 있으므로 실제 집중 시간으로 단정하지 않는다. 반복 시도·동일 문제를 새로운 범위 학습 완료로 중복 집계하지 않는다.

### 6.4 시간 제약과 배치

날짜별 잔여 가용 시간 = 공부 가능 시간 - 해당 날짜의 기존 수동·고정 예약 - 오늘 이미 사용한 공부 시간.

완료 작업의 실제 시간이 없으면 예정 시간을 추정치로 사용하고 표시한다. 같은 활동의 실제 기록과 완료 예정 시간을 둘 다 차감하지 않는다. 고정 작업만으로 예산을 초과했다면 새 작업을 넣지 않고 충돌을 알린다.

배치 절차:

1. 사용자·과목·범위·날짜와 가용 시간을 검증한다. 기본 7일, 최대 30일 등 계획 범위를 설정한다.
2. 완료·진행 중·수동·고정 항목을 먼저 보존하고 각 날짜의 잔여 시간을 계산한다.
3. 선택 기간 내 마감까지 필요한 예상 시간과 누적 가용 시간을 비교해 부족 위험을 표시한다. 기간 밖 마감은 기간 밖 시간을 계산하지 않은 채 가능·불가능으로 확정하지 않는다.
4. 마감·준비 여유가 적은 활동을 먼저 고려하고, 그 안에서 복습 기한, 취약 근거, 미완료 경과, 중요도와 과목 편중을 반영한다.
5. 읽기·설명 확인 → 독립 문제 풀이 같은 선후 관계를 지키고, 가능한 날짜의 남은 시간에 분할 배치한다.
6. 낮은 우선순위 활동을 이동해 임박한 마감·선행 작업이 들어갈 수 있는지 한 번 더 조정한다.
7. 날짜별 총시간, 휴식일, 마감, 선후 관계, 중복, 고정 항목 보존을 별도 검증기로 검사한다.
8. 남은 활동은 미배치 목록과 사유·부족 시간으로 반환한다. 시간 제한을 깨거나 목록 밖으로 숨기지 않는다.

가중치·최소 세션 길이·복습 우선순위는 버전 있는 정책으로 관리한다. 최소 세션보다 짧은 시간만 남으면 시간을 과다 배정하는 대신 비워 두거나 실행 가능한 짧은 활동을 선택한다. 처음부터 복잡한 최적화 라이브러리를 도입하지 않는다.

### 6.5 모드와 재계획

- 가볍게: 선택 활동·목표 사용량을 줄인다. 임박한 필수 작업을 숨기지 않고 부족분을 설명한다.
- 집중: 가용 시간 안에서 추가 활동·응용 문제 비중을 높인다. 사용자 예산은 늘리지 않는다.
- 과제/시험 중심: 해당 목표의 후보 우선순위를 조정하되 고정 작업·마감 제약은 유지한다.
- 다시 제안: 선호·과목 균형을 바꾼 대안을 비교한다. 같은 입력의 결과를 임의로 바꾸기 위해 LLM을 호출하지 않는다.
- 미완료: 완료한 분량은 보존하고 남은 부분만 재배치한다.
- 진단 변화: 보완이 확인되면 이후 보충 작업을 줄이고, 미확정 개념은 확인 작업으로 바꾼다.
- 가용 시간·시험일 변경: 영향을 받는 기간·활동만 다시 계산한다. 다른 과목의 미래 계획 전체를 삭제하지 않는다.
- 적용 방식: 추가/이동/유지/미배치의 차이를 보여주고 사용자가 적용한다. 단순 조회·체크·자동 저장이 전체 계획 재생성을 유발하지 않는다.

첫 버전의 재계획은 앱 내 명시적 실행 또는 변경 후 제안으로 제공한다. 서버 예약 실행·백그라운드 알림·자동 캘린더 수정은 별도 단계다.

### 6.6 API·저장·화면

- POST /study-plan/preview: 선택한 목표·기간·모드·가용 시간 예외를 받고 서버가 인증 사용자 데이터를 읽어 초안을 만든다.
- 응답: policy_version, input_revision, 날짜별 items·예산·여유, reasons, unscheduled, warnings, 변경 전후 차이.
- POST /study-plan/apply: 미리보기 ID와 base_revision으로 원자적으로 적용한다. 그사이 다른 화면에서 변경됐으면 충돌을 반환하고 다시 미리보기 한다.
- PATCH /study-plan/items/{id}: 완료·부분 완료·이동·고정 변경. 실제 학습 근거·진도와 계획 체크를 구분한다.
- 신규 항목은 명시적인 date와 origin=planner를 사용한다. 기존 origin=ai는 이전 생성 방식으로 구분한다.
- Dashboard와 Calendar는 하나의 계획 서비스·데이터를 사용한다. 기존 plans JSON 전체 저장 effect를 신규 항목에 병행 적용하지 않는다.
- 기존 수동 계획은 ID·완료 상태를 보존해 일회성 전환한다. 날짜 없는 과거 항목은 날짜를 추정해 과거 완료로 만들지 않고 미배정 항목으로 확인시킨다.
- pacePlans는 진도·분량 정보로 활용한다. 같은 범위가 새 계획 활동과 기존 자동 분량 칩에 이중 배치되지 않게 화면 표시 역할을 조정한다.
- 기존 dashboard_state의 plans는 호환 읽기·전환 완료 뒤 쓰기 중단 순서를 정한다. 마이그레이션·롤백 동안 두 저장소가 동시에 정답이 되지 않게 한다.
- 화면: 요일별 시간·날짜 예외 설정, 계획 미리보기, 추천 이유, 활동별 예상 시간, 시간 부족 안내, 고정·이동, 적용·되돌리기를 제공한다.
- 각 항목은 자료·페이지·개념·문항까지 연결한다. 과목 홈으로만 이동하는 현재 링크를 구체화한다.

### 6.7 복습 알고리즘 연결

복습 시점 계산과 계획 날짜 배분은 분리한다. 계획 엔진은 복습 시스템이 제공한 due_at을 입력으로 사용한다. 초기에는 버전이 있는 단순 복습 정책으로 시작할 수 있고, 복습 카드·결과 이력이 준비되면 FSRS 기반 due_at으로 교체한다. 이번 계획에 FSRS 전체 구현을 숨은 필수 조건으로 넣지 않는다.

### 6.8 수정 파일·완료 기준

- 서버 신규: study_planning의 후보 생성·시간 추정·배치·검증·적용 서비스와 테스트.
- 서버 수정: main.py의 기존 /study-plan, schemas.py, prompts.py. 전환 기간의 기존 응답 호환성을 정의한다.
- 프론트 수정: studyPlan.ts, studyPlanner.ts, dashboardState.ts, pace.ts, Dashboard.tsx, Calendar.tsx, PlannerModals.tsx.
- 프론트 신규: 계획 미리보기·요일별 가용 시간·충돌/미배치 안내·개념 연결 서비스.
- DB: preferences, revisions, items와 원자적 적용·소유자 권한, 기존 계획 전환 SQL.

완료 기준:

1. 날짜별 시간 상한·휴식일·마감·선후 관계·고정 항목을 고정 테스트에서 지킨다.
2. D-day 없이 복습·취약 개념만 있어도 계획이 생성된다. 작업이 없으면 정상적인 빈 계획을 반환한다.
3. 시간이 부족하면 부족량과 미배치 활동이 표시된다. 항상 모든 공부가 완료 가능하다고 안내하지 않는다.
4. 같은 입력·기준 시각·정책에서는 재현 가능한 계획이 나온다. 추천 이유는 실제 입력 근거를 사용한다.
5. 계획 생성·재계산은 LLM 키 없이도 동작한다.
6. 완료·부분 완료·수동·고정·선택하지 않은 범위가 재계획에서 보존된다.
7. 대시보드·캘린더 동시 수정·자정·시간대·시험일 변경을 검사한다.

## 7. 세 기능이 연결되는 예시

예시: 자료구조 시험을 준비하는 학생이 이진 탐색 관련 서로 다른 문제에서 반복해서 조건 범위를 틀린다.

1. 진단: 이진 탐색/경계 조건 개념에 근거가 쌓인다. 조건 해석 원인은 학생 확인 또는 풀이 근거가 있을 때 기록한다.
2. 검색: 튜터가 현재 강의자료의 경계 조건 설명·예제 구간을 찾아 자료명·페이지와 함께 제시한다.
3. 보완: 학생이 설명·예제를 확인하고 관련 개념의 다른 문제를 푼다.
4. 계획: 오늘 가용 시간에 15분 보완 + 10분 확인 활동을 넣고, 다른 수동·고정 작업과 합쳐 예산을 검사한다.
5. 추적: 자료를 읽었다는 이유만으로 안정 상태로 바꾸지 않는다. 이후 독립 수행과 지연 재평가 결과를 근거로 갱신한다.
6. 재계획: 상태가 좋아지면 이후 보충 시간을 줄이고 다른 개념에 배분하는 초안을 보여준다.

이 예시의 활동 시간은 설명용이다. 실제 시간은 사용자 예산·분량·시간 추정 정책에 따라 계산한다.

## 9. 평가와 우선 완료 기준

- 검색: 원문 근거가 있는 질문, 같은 용어의 다른 자료, 영문 별칭, 코드·수식, 다중 턴, 답이 없는 질문, 원문 변경·삭제를 포함한다.
- 진단: 틀린 답 하나, 반복된 같은 문제, 다른 문제의 반복 오답, 힌트 후 정답, 과잉 확신, 잘못된 문항, 보완 후 재평가를 포함한다.
- 계획: 가용 시간 0분, 예산 부족, 여러 시험, 수동 계획 충돌, 복습만 존재, 마감 경과, 부분 완료, 입력 변경·동시 적용을 포함한다.
- 정책 검증은 fixture와 일반 코드 테스트로 수행한다. LLM을 쓰는 답변·원인 후보 평가는 별도 비용 상한과 사람 검토로 비교한다.
- 보고서에서 검색 근거의 존재·답변 사실성·원인 추정 정확도·일정 제약 충족·실제 학습 성과를 서로 다른 지표로 다룬다.
- 초기 통합 완료: 과목 하나·자료 하나로 오답 근거 확인 → 원문 검색·튜터 보완 → 계획 배치 → 다른 문제 재평가가 작동한다.

## 10. 후속 확장

1차 이후 평가로 필요성이 확인되면 의미 검색·복합 검색, 선수지식 그래프, 개인별 시간 추정, FSRS 복습 카드, 예약 재계획·알림, 외부 시간표 연동을 추가한다. 녹음/STT·데스크톱 캐릭터·장기 추천 모델은 이번 세 기능의 필수 범위에서 제외한다.

## 11. 제품 흐름 — 학습 세션으로 연결

추가 요구: 학생이 편하게 직접 떠올리고 설명하고 해결하며, 그 결과가 이후 복습·학습 결정에 이어지는 경험을 제공한다. 앞의 검색·진단·계획 기능은 이 학습 세션의 내부 기능으로 연결한다.

### 11.1 진입점과 사용자 경험

- 대시보드의 주요 행동은 오늘 학습 시작 또는 이어서 학습으로 둔다. 과목·자료·범위는 선택한 계획이나 마지막 활동에서 가져온다.
- 시작 전에 사용 가능 시간만 간단히 선택하고 수정할 수 있게 한다. 5분이면 짧은 회상·확인, 15분이면 회상·보완·재확인, 긴 시간이면 새로운 범위 학습을 포함하는 안으로 시작한다. 시간은 목표 분량을 조절하는 입력이며 강제 종료 타이머가 아니다.
- 수업 전 준비, 수업 중 자료 보기, 수업 후 회상, 예정된 복습은 서로 다른 진입 문맥이다. 매번 모든 단계를 밟는 긴 마법사로 만들지 않는다.
- 처음 배우는 내용이면 짧은 설명·예제를 먼저 제공한 뒤 회상·확인으로 이어간다. 수업을 들었거나 복습하는 내용은 회상부터 시작한다. 기존 familiarity 정보를 재사용하고 사용자가 시작 방식을 바꿀 수 있게 한다.
- 한 화면에는 현재 질문·활동과 다음 행동을 둔다. 원문·요약·튜터는 필요할 때 옆에서 펼친다.
- 회상 화면의 기본 상태는 자료가 접힌 상태다. 모르겠어요·도움 받기·요약 바로 보기·나중에 하기를 제공하고 사용 이력을 기록한다. 자료를 보지 못하게 강제로 잠그지 않는다.
- 사용자가 고르는 것은 학습 시간, 답변, 필요한 도움 정도다. 문제 유형·난이도·요약 형식을 매번 다시 설정하지 않게 기본값을 제안한다.
- 작성 중 답변·현재 단계·도움 사용·남은 활동을 저장하고 중단 지점부터 재개한다. 완료 확인·설정 입력을 단계마다 반복하지 않는다.

### 11.2 여섯 단계의 제품 동작

| 학습 시점 | 기본 화면·행동 | 시스템이 준비할 것 | 기록·다음 행동 |
| --- | --- | --- | --- |
| 수업 전 | 오늘 주제와 관련된 이전 개념 1~2개 확인 | 근거가 확인된 선수 개념·짧은 진단 | 아는 부분은 통과, 모르는 부분만 짧게 설명 |
| 수업 중 | 현재 슬라이드와 헷갈림/질문 표시 | 해당 슬라이드 문맥·개념 연결 | 질문함과 수업 후 회상 후보에 반영 |
| 수업 직후 | 자료를 접고 한 질문씩 짧게 설명 | 원문 기반 핵심 질문·평가 기준 | 정확한 내용·빠진 조건·혼동 지점 피드백 |
| 보완 | 부족한 한 개념의 원문·힌트 확인 | 출처와 단계별 도움·연습 문제 | 다른 표현·조건의 문제로 재확인 |
| 며칠 후 복습 | 정답을 보지 않고 다시 답하기 | 기한이 된 개념과 회상/적용 문제 | 도움 없는 성공·실패로 다음 복습 조정 |
| 장기 확인 | 다른 맥락의 문제·이전 개념을 섞은 확인 | 개념별 수행 근거·아직 미평가인 능력 | 다음 범위 진행·추가 보완·유지 복습 결정 |

1~2개 질문과 시간 길이는 시작용 UX 가설이다. 실제 이탈률·응답 부담·학습 근거를 보고 조정한다.

### 11.3 수업 전·중의 부담 줄이기

1. 선수지식은 현재 자료에 필요한 소수 개념부터 연결한다. 필수 선행 관계와 단순 관련 관계를 구분하고 AI 제안은 근거·검토 상태를 기록한다.
2. 선수 개념 수행 근거가 없으면 짧게 확인한다. 최근 독립 수행 근거가 충분하면 건너뛰거나 사용자가 직접 확인하도록 한다.
3. 슬라이드 전체에 이해 상태 입력을 요구하지 않는다. 헷갈림·나중에 질문을 한 번에 표시할 수 있게 하고, 이해함 표시는 선택으로 둔다.
4. 표시하지 않은 슬라이드는 미기록이다. 이해함·미이해·미학습으로 추정하지 않는다.
5. 질문은 선택 구절·슬라이드와 함께 저장하고, 해결한 질문과 남은 질문을 구분한다. 질문 여부는 취약 판정과 분리한다.
6. 녹음은 후속 모듈로 둔다. 녹음→STT→시각 정보가 있는 구간 병합→슬라이드 연결→강의 노트 순서로 연결하고, 전사 내용을 실시간 이해도 근거로 직접 사용하지 않는다. 수업 녹음의 사용자 권한·학교 정책·참여자 동의와 보관·삭제 설계는 이 모듈 착수 시 확인한다.

### 11.4 수업 직후 15분 세션 예시

| 활동 | 예시 시간 | 학생이 하는 일 |
| --- | --- | --- |
| 회상 | 2분 | 핵심 개념을 짧은 문장·글머리표로 설명 |
| 피드백 | 3분 | 맞는 부분·빠진 조건·혼동한 연결 확인 |
| 필요한 보완 | 5분 | 해당 원문·예제를 보고 단계별 도움 받기 |
| 독립 확인 | 4분 | 표현·조건을 바꾼 문제를 도움 없이 해결 |
| 마무리 | 1분 | 오늘 확인된 내용과 다음 복습 확인 |

시간은 예시다. 잘 아는 개념의 보완은 건너뛰고, 답하지 못하는 학생을 빈 답안 화면에서 오래 붙잡지 않는다. 시도 후 짧은 도움을 제공하고 독립 확인 기회를 다시 준다. 한 세션에서 해결하지 못하면 재평가 대기로 남기며 같은 개념의 재시도를 무한 반복하지 않는다.

### 11.5 자기 설명 피드백

- 질문별로 원문 근거, 기대 개념, 필수 조건·인과 연결, 허용되는 표현 차이, 대표적인 혼동을 평가 기준으로 준비한다.
- 학생의 설명을 원문과 평가 기준에 대조해 잘 설명한 부분, 빠진 내용, 잘못 연결한 부분, 다음 확인 질문을 반환한다.
- 학생 답변의 해당 구절과 관련 원문 위치를 함께 보여준다. 답안 전체를 모범답안으로 교체하는 화면보다 차이를 짧게 보여주는 방식으로 시작한다.
- 자유 서술의 의미 평가는 선택적으로 LLM을 사용하고 구조화된 결과·근거를 검사한다. 근거가 불확실하면 확인 필요로 반환한다.
- 완벽한 표현·긴 글을 요구하지 않는다. 첫 버전은 짧은 텍스트·글머리표 입력, 객관식·단답형 보조 확인을 제공한다. 음성 자기 설명은 STT 입력 모듈 이후 추가한다.
- 설명을 잘했어도 계산·응용·기억 유지가 확인된 것은 아니다. 수행 종류별 결과를 따로 기록한다.

### 11.6 튜터 모드와 도움 기록

| 모드 | 제공 행동 | 진단에서의 처리 |
| --- | --- | --- |
| 설명 | 원문 기반 설명·예제·풀이 | 학습 노출·보완 활동 |
| 학습 | 관련 개념 → 접근 방법 → 첫 단계 → 추가 설명 | 사용한 힌트 수준을 기록한 수행 |
| 시험 | 평가 문항, 제출 뒤 피드백 | 시험 중 정답·힌트를 받지 않은 독립 수행 |

세션 문맥에 맞는 모드를 기본 적용하고 사용자가 변경할 수 있게 한다. 도움 요청은 그때까지의 독립 시도와 이후 도움을 받은 수행을 구분해 남긴다. 시험 모드의 제한은 UI 버튼뿐 아니라 서버의 답변·도구 정책에도 적용한다. 모드 변경·정답 열람·힌트 사용이 있는 결과를 도움 없는 평가와 섞지 않는다.

### 11.7 이해도는 네 가지 근거로 표시

| 능력 | 근거 | 아직 확인되지 않은 경우 |
| --- | --- | --- |
| 개념 이해 | 자기 말로 정의·관계·이유 설명 | 설명 확인 필요 |
| 기초 적용 | 예제와 유사한 문제의 독립 해결 | 적용 문제 미평가 |
| 전이·응용 | 풀이 원리가 같은 다른 조건·맥락 문제 | 새로운 조건 미평가 |
| 기억 유지 | 일정 시간이 지난 뒤 도움 없는 회상·해결 | 지연 평가 대기 |

한 개의 이해도 퍼센트로 이 네 가지를 합치지 않는다. 첫 세션이 끝나면 오늘 확인한 능력만 보여주고, 기억 유지·응용은 아직 미평가일 수 있음을 그대로 표시한다. 확신도·슬라이드 이해 표시는 자기 보고로 별도 보관한다.

### 11.8 복습·교차 학습과 다음 계획

1. 세션 종료 시 개념·수행 결과·도움 수준과 복습 기한을 저장한다. 다음 날·며칠 후 일정은 초기 정책안이며 고정된 보편적 망각률로 계산하지 않는다.
2. 복습은 원문 다시 읽기보다 먼저 회상·독립 문제로 시작하는 것을 기본 흐름으로 제안한다. 실패하면 필요한 원문·도움을 제공한다.
3. 기초 수행이 부족하면 예제를 포함한 같은 개념의 연습을 제공한다. 구분 연습이 필요한 단계에서는 관련 개념·유형을 섞는 문제 묶음을 제안한다. 무관한 과목을 임의로 섞지 않는다.
4. 표현만 바꾼 문제, 조건이 바뀐 문제, 새로운 응용 문제를 구분한다. AI가 만든 변형 문제도 원문 근거·정답·난이도 검증 후 사용한다.
5. 새 문제는 실제 학생 답변 전에 정답을 숨긴 상태로 제공한다. 방금 본 정답의 단순 반복은 지연 기억 유지 근거로 계산하지 않는다.
6. 학습 계획은 시험·가용 시간뿐 아니라 부족한 수행 종류를 고려한다. 개념 설명은 가능하지만 적용이 어려우면 추가 요약보다 적용 문제를 배치한다.
7. 복습 적체가 생기면 오늘의 예산·마감·필요도를 반영해 일부를 배치하고 나머지를 표시한다. 무한히 늘어나는 의무 목록과 반복 알림으로 만들지 않는다.

### 11.9 추가 구현 단위

- learning_sessions: 사용자·과목·자료 버전·개념 범위·목표 시간·진입 문맥·현재 상태·정책 버전·재개 정보.
- learning_session_steps: 질문·활동·답변 초안·도움 수준·채점 상태·완료·중단·재시도와 기록 시각. 중복 제출 방지 키와 수정 버전을 둔다.
- slide_annotations / learning_questions: 페이지·선택 구절·이해 표시·질문·해결 상태.
- learning_rubrics: 원문과 연결된 기대 개념·필수 조건·허용 답안·버전.
- 기존 concept_learning_evidence에 수행 종류·세션·지연 시간·도움 수준을 연결한다. 개념 집계·계획 입력은 여기서 파생한다.
- 세션 API: 시작, 답변 임시 저장, 제출·평가, 힌트 요청, 다음 활동, 중단·재개, 종료. 서버가 상태 전이와 버전을 검증한다.
- 별도 학습 세션 화면을 추가하고, 기존 Summary/Quiz/AITutor의 본문·문항·원문·설명 UI를 공유한다. 거대한 페이지 파일을 그대로 새 화면 안에 중첩하지 않는다.
- 기본 상태는 준비→회상→피드백→필요 시 보완→독립 확인→마무리다. 서버의 단순 상태 전이·정책 함수로 구현한다. 다음 단계마다 LLM이 실행 흐름을 결정하게 하지 않는다.
- 답변 저장·채점 완료·계획 완료 이벤트는 중복 수신에도 한 번만 반영한다. 평가 요청 재시도는 같은 학생 답변을 여러 독립 수행으로 만들지 않는다.
- 원문·개념·문항·평가 기준이 바뀌면 생성 당시 버전을 보존한다. 학습 결과와 평가 실패를 구분하고, 모델 장애 시 답안을 유지해 재시도·자기 점검으로 이어갈 수 있게 한다.

### 11.10 첫 제품 범위와 구현 순서

앞의 8절은 기반 기능의 분할안이다. 실제 제품은 아래 사용자 흐름을 첫 수직 구현 범위로 삼고 필요한 기반만 함께 만든다. 모든 테이블·검색·진단·계획을 완성한 뒤 학생 화면을 붙이는 일정으로 진행하지 않는다.

| 순서 | 구현 범위 | 완료 기준 |
| --- | --- | --- |
| 1 | 자료 하나의 개념·원문 연결, 짧은 회상, 근거 피드백 | 학생 답안과 원문의 차이를 확인 |
| 2 | 필요한 원문·단계별 도움, 다른 문항 재확인, 중단·재개 | 한 번의 학습 세션 완주 |
| 3 | 기한이 있는 복습·독립 수행 기록·간단한 다음 활동 | 다른 날 같은 개념을 재확인 |
| 4 | 개념별 네 수행 지표·원인 확인·검색 범위 확장 | 근거에 따라 보완 활동 선택 |
| 5 | 요일별 시간·마감·복습을 반영한 계획과 재조정 | 학습 결과가 다음 날짜 행동으로 연결 |
| 6 | 수업 전 짧은 진단·수업 중 표시·소규모 선수관계 | 수업 전후 활동이 자료·개념으로 연결 |
| 후속 | 녹음·STT·슬라이드 연결·음성 자기 설명 | 강의 기록이 원문 근거·질문함에 연결 |

최소 기능은 자료 1개·핵심 개념 2~3개·회상 질문·피드백·보완·다른 문항 확인·다음 복습이다. 전체 개념 그래프·자동 시간표·STT 없이도 검증할 수 있다. 전공에 따라 회상·계산·설명 과제의 비중을 조정한다.

### 11.11 편의성과 학습 효과 검증

- 편의성: 시작까지 필요한 선택 수, 첫 답변까지 걸린 시간, 단계별 이탈, 중단 뒤 재개 성공, 불필요한 보완 건너뛰기를 측정한다.
- 학습 근거: 힌트 없는 설명·적용·새 조건 문제·지연 평가를 각각 측정한다. 학습시간·요약 열람·AI 대화 수를 성과의 대리 지표로만 사용하지 않는다.
- 피드백 신뢰도: 원문에 의해 지지되는 피드백, 잘못된 채점, 불필요한 보완 추천, 변형 문제의 정답 오류를 사람 기준으로 평가한다.
- 파일럿: 기존 요약·퀴즈 흐름과 새 세션 흐름을 비슷한 학습 시간·사전 수준에서 비교한다. 평가 문제는 연습 문항과 분리하고 가능하면 배정 순서를 무작위화한다. 자료·난이도·참가자 수와 차이를 보고한다.
- 지연 평가를 놓친 사용자를 제외한 결과만으로 전체 효과를 주장하지 않는다. 참여율·누락률과 학습 결과를 함께 보고한다.
- 초기 목표는 회상·보완·재확인·다음 복습의 연결과 사용 부담 검증이다. 학습 효과 개선은 실제 평가 결과로 판단한다.

### 11.12 설계 참고 연구

- Roediger & Karpicke (2006), Test-enhanced learning: https://pubmed.ncbi.nlm.nih.gov/16507066/ — 해당 실험에서 지연 검사 시 인출 연습의 기억 유지 이점을 보고했다. 모든 과목·학생의 효과 크기로 일반화하지 않는다.
- Cepeda et al. (2008), Spacing Effects in Learning: https://doi.org/10.1111/j.1467-9280.2008.02209.x — 복습 간격과 목표 기억 유지 기간의 관계를 조사했다. 모두에게 동일한 1·3·7일이 최적이라는 근거로 사용하지 않는다.
- Rohrer & Taylor (2007), The shuffling of mathematics problems improves learning: https://eric.ed.gov/?id=EJ786797 — 수학 문제 연습의 분산·혼합 조건을 비교했다. 제품의 모든 유형에 무작위 혼합을 적용하는 근거로 확대하지 않는다.
