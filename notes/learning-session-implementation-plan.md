# 학습 세션 구현 상세 계획

구현 상태(2026-11-22): 첫 버전의 세션 API·Supabase 마이그레이션·학습 화면·AI 준비/평가·저장/재개를 구현했다. 구현 파일과 실행 설정은 README.md의 학습 세션 항목을 참고한다. 아래는 구현에 사용한 원래 계획이며, 운영 DB 마이그레이션·서버 전용 키 설정과 실제 자료 파일럿은 아직 수행하지 않았다. 브라우저는 테스트 자료와 저장 어댑터로 검증했고, DB 권한·원자성은 별도 임시 PostgreSQL에서 검증했다.

작성일: 2026-11-19 / 코드 기준: main, 4488bd5 / 버전: 1.0, 자체 검토 수정 반영

학습 세션만 구현하는 계획이다. 기존 품질·운영 개선 계획과 전체 새 기능 계획을 선행 과제로 요구하지 않는다. 현재는 계획·검토 문서 작성 단계이며 애플리케이션·DB 구현이나 동작 테스트는 수행하지 않았다. 자체 검토 근거와 수정 내역은 learning-session-plan-review.md에 기록한다.

## 1. 목표와 범위

학생이 자료 하나의 핵심 개념을 직접 설명하고, 부족한 부분을 원문·힌트로 보완한 뒤 다른 문항으로 확인하는 한 번의 학습 세션을 제공한다.

- 기본 15분·개념 2개, 최대 3개. 시간은 분량을 고르는 참고값이며 강제 종료 기준이 아니다.
- 진입은 자료 상세의 학습 시작, 재개는 대시보드의 이어서 하기와 세션 URL.
- 텍스트·페이지 마커가 있는 변환 자료를 우선 지원하고, 짧은 범위는 페이지 없이도 지원한다.
- 포함: 범위 선택, 준비, 회상, 근거 피드백, 원문·힌트, 객관식 확인, 요약 결과, 저장·재개.
- 제외: 전체 과목 검색, 전공 개념 그래프, 오답 원인 확정, FSRS, 자동 복습 일정, 학습 계획 최적화, STT, 음성 입력, 시험 서비스.
- 세션 안 개념은 원문 위치와 연결된 로컬 ID다. 전체 개념 DB 구축을 선행하지 않는다.
- 종료 화면은 다음 학습 제안만 표시한다. 자동 일정이 생성됐다고 안내하지 않는다.
- 첫 대상은 원문 텍스트로 근거를 확인할 수 있는 개념 설명이다. 이미지 관찰만으로 답을 정해야 하는 문제, 복잡한 증명·코드 실행·수식 동치 채점은 제외한다. 수식·코드의 화면 표시는 기존 렌더링을 활용한다.
- 준비 결과가 개념 1개만 충분히 지지하면 1개로 진행한다. 분량을 맞추기 위해 원문에 없는 개념을 추가하지 않는다.
- 학습 세션 기록은 첫 버전에서 quiz_attempts·기존 총 학습시간·페이스 진도에 합산하지 않는다. 중복 집계와 지표 의미 변경을 피하고 결과 화면에서만 조회한다.

## 3. 화면별 동작

| 화면 | 학생 행동 | 저장·다음 단계 |
| --- | --- | --- |
| 시작 | 자료·범위·수업 들음/처음 학습 확인 | 세션·원문 스냅샷 생성 |
| 준비 | 현재 준비 상태 확인 | 개념·질문·기준·힌트·확인 문제 생성 |
| 회상 | 짧은 설명·글머리표, 모르겠어요, 도움 요청 | 답변·도움 사용 저장 후 평가 |
| 피드백 | 맞은 내용·누락·혼동·근거 확인 | 필요하면 보완, 충분하면 확인 문제 |
| 보완 | 원문·두 단계 힌트·모범 설명 선택 | 노출 이력 저장 후 확인 문제 |
| 확인 | 다른 표현·조건의 객관식 한 문제 | 일반 코드로 채점 후 개념별 다음 단계 |
| 종료 | 오늘 확인된 내용과 남은 부분 확인 | 완료·건너뜀·평가 불가를 구분한 결과 저장 |

처음 학습이면 짧은 원문·예제를 먼저 제공한다. 수업 후 복습이면 회상부터 시작한다. 기존 요약·자료 화면에 직접 접근하는 동선은 계속 제공한다.

### 3.1 구체적인 화면 계약

- 시작 기본값: 선택된 자료·전체 또는 마지막 선택 범위·15분·개념 2개·수업 후 회상. 처음 학습은 한 번의 선택으로 바꾼다. 자료·과목을 다시 고르게 하지 않는다.
- 원문이 상한보다 길면 페이지·제목 범위를 고르는 화면만 추가한다. 자동으로 앞부분을 잘라 학습 범위를 바꾸지 않는다.
- 회상 입력은 짧은 텍스트·글머리표를 허용한다. 글자 수를 채워야 제출되는 최소 분량 조건은 두지 않고 빈 답변은 모르겠어요와 구분한다. 답변 상한은 초기 4,000자로 UI·서버에서 일치시키고 설정으로 조정한다.
- 원문·힌트는 접힌 도움 영역에 둔다. 모바일은 본문 아래 펼침, 넓은 화면은 옆 영역으로 표시한다. 사용자가 답안을 쓰던 위치·내용을 유지한다.
- 도움·자기 점검·건너뛰기는 선택 행동이다. 피드백 뒤 충분히 설명했으면 바로 확인 문제로 진행할 수 있다.
- 종료의 표현은 세션 마침, 설명에서 확인된 부분, 확인 문제 결과, 남은 확인이다. 완료 배지를 전체 개념 이해·시험 준비 완료로 표현하지 않는다.
- 다른 문항은 원문에서 지지되는 표현·조건을 바꾼 객관식으로 제한한다. 1차 확인은 기초 확인이며 응용·전이의 독립 검증으로 이름 붙이지 않는다.

## 4. 원문과 학습 묶음 준비

1. 서버가 인증 사용자 소유의 course_id와 material_id로 실제 Markdown을 읽는다.
2. 선택 페이지·섹션을 엄격하게 검증한다. 존재하지 않는 범위를 전체 원문으로 조용히 대체하지 않는다.
3. 초기 입력 상한은 선택 범위 12,000자로 두고 조정 가능하게 한다. 길면 범위를 줄이도록 안내한다.
4. 선택 원문·이름·위치·해시·처리 버전을 세션용 스냅샷으로 저장한다.
5. 한 번의 준비 호출로 개념 2개, 회상 질문, 평가 기준, 원문 참조, 힌트, 모범 설명, 확인 문제를 구조화해 생성한다.
6. 기준·힌트·정답은 서버에 저장한다. 프론트에는 현재 단계의 공개 필드만 반환한다.
7. 개념·문항·평가 기준·원문 구간에 안정적인 ID를 부여하고, 출처와 객관식 정답 인덱스를 검사한다.
8. 같은 사용자·자료·범위·실제 모델·생성 정책의 준비 결과는 재사용할 수 있다. 실패한 묶음은 재사용하지 않는다.

### 4.1 원문 범위 계약

- 페이지 표기는 PDF p.N과 PPT 슬라이드 마커를 구분해 해석한다. 자료 하나만 대상으로 하므로 서로 다른 파일의 p.1을 합치지 않는다.
- 마커가 있는 자료는 실제 페이지 집합과 선택을 대조한다. 없는 페이지가 섞이면 수정 요청을 반환한다. 빈 선택은 전체로 명시적으로 정규화한다.
- 마커가 없는 짧은 자료는 전체, 긴 자료는 제목 경계 선택을 지원한다. 제목도 없으면 시작·끝 문단을 고르게 하고 안정적인 문단 ID로 저장한다.
- 현재 server/main.py의 _filter_markdown_by_pages는 잘못된 범위를 원문 전체로 폴백할 수 있으므로 새 경로에서 그대로 호출하지 않는다. 기존 요약·퀴즈의 동작은 이번 PR에서 바꾸지 않는다.
- 입력을 source_units로 나누고 각 단위에 unit_id, type(text/table/code/math/derived), 원문 offset, 실제 페이지/섹션 라벨을 둔다. 추출이 불확실한 시각 분석은 확정 평가 근거에서 제외한다.
- 스냅샷은 선택 원문과 단위 위치를 보존한다. 자료의 전체 Markdown 해시도 기록해 현재 자료 변경을 감지한다. 원문이 바뀌면 이전 자료 기준 세션임을 표시하고 새 세션 시작을 선택하게 한다. 진행 중 기준을 자동 교체하지 않는다.
- 원문 텍스트를 서버에서 읽고 범위를 계산한다. 클라이언트가 제출한 원문·정답·자료 소유자 정보를 신뢰하지 않는다.

### 4.2 비공개 학습 묶음 계약

각 concept에는 local_concept_id, 제목, source_unit_ids, 짧은 도입, recall_question, rubric_criteria, hints[2], reference_explanation, verification_question을 둔다.

- rubric_criteria: criterion_id, 기대 개념·필수 조건, 근거 unit ID와 인용 구간, 허용 표현·혼동.
- verification_question: 안정적인 question_id, question, options, answer_index, explanation, source_refs. 1차는 객관식만 지원한다.
- 서버가 ID·선택지 수·정답 범위·원문 참조·빈 필드·중복 문제를 검사한다. 근거 인용은 실제 source_unit의 부분 문자열인지 확인한다.
- 구조 검증을 통과해도 사실성·난이도가 보증되는 것은 아니다. 내부 파일럿 자료는 사람이 원문·정답·힌트를 검토한다. 학생은 잘못된 문항 신고를 할 수 있고 신고 항목은 확인 필요로 표시한다.
- 캐시 키는 사용자·과목·자료 ID·원문/범위·개념 수·실제 모델·프롬프트·처리 버전을 포함한다. 세션 진입 문맥은 세션에 기록하며 준비 내용이 문맥에 따라 달라지면 키에도 포함한다.
- 재사용한 문항의 이전 노출 여부를 기록한다. 같은 준비 묶음의 재학습은 새로운 독립 문항 평가로 합산하지 않는다.
- 최종 결과·힌트·도입·문제 표시는 저장된 묶음으로 처리한다. 생성 완료 뒤 학생 클릭마다 추가 생성을 하지 않는다.

## 5. 상태 전이

세션 수명: preparing → active → completed. 사용자는 active에서 paused로 이동·재개하거나 abandoned로 종료할 수 있다. 준비 실패는 failed로 남겨 재시도한다.

개념별 진행: recall_answering → recall_evaluating → recall_feedback → 선택적 repair → check_answering → check_feedback → done. 다음 개념이 있으면 반복하고, 없으면 결과 화면으로 이동한다.

- 도움 요청·원문 열람은 별도 노출 기록이다.
- 일시 중단은 현재 단계·답변을 보존한다.
- 모르겠어요·건너뛰기는 오답과 구분한다.
- 평가 실패는 미평가로 남기며 학생의 오답으로 바꾸지 않는다.
- 다음 단계와 전체 완료는 서버가 판단한다.

### 5.1 상태별 허용 행동

| 현재 상태 | 행동 | 결과 |
| --- | --- | --- |
| preparing | 조회·마치기 | 완료된 준비만 active 전환. 실패는 retryable 표시 |
| recall_answering | 초안·제출·모르겠음·도움·건너뛰기 | 제출은 답변을 고정하고 평가 요청 생성 |
| recall_evaluating | 조회·일시 중단·마치기 | 답변 수정 차단. 평가 실패 시 retry/자기 점검 제공 |
| recall_feedback | 보완 보기·확인 문제로 진행 | 검증된 기준에서 누락/혼동이 있으면 보완을 기본 추천 |
| repair | 원문·힌트·모범 설명·진행 | 도움 노출을 저장한 뒤 확인 문제 공개 |
| check_answering | 선택·제출·도움·건너뛰기 | 선택은 한 번 고정. 도움을 받으면 assisted로 기록 |
| check_feedback | 다음 개념·마치기 | 같은 확인 문제를 정답이 될 때까지 반복하지 않음 |
| failed(준비 실패) | 범위 수정·준비 재시도·마치기 | 준비된 문항이 없으므로 회상·자기 점검 화면은 열지 않음 |
| completed/abandoned | 결과 조회·새 세션 | 원래 제출·단계의 재작성 불가 |

처음 학습은 도입 노출 뒤 recall_answering으로 진입한다. 회상 도움은 사용자가 언제든 열 수 있다. 모르겠어요는 LLM 평가 없이 보완을 추천하고, 건너뛰기는 미평가로 남긴다.

건너뛰기 대상도 명시한다. 이 개념은 나중에는 현재 개념 전체를 미수행으로 마치고 다음 개념으로, 확인 문제 건너뛰기는 확인만 미평가로 남긴다. 모르겠어요는 원문·보완으로 이어간다. 원문만 열기는 현재 초안을 유지하며 도움 이력만 추가한다.

### 5.2 판정·중단 정책

- 회상 충분: 모든 필수 기준이 met이고 모순·미확정이 없을 때. 누락/모순이면 보완 추천, uncertain이면 확인 필요다. 숫자 점수 하나로 분기하지 않는다.
- 보완 직후 확인 문제 실패는 남은 확인으로 남기고 다음 개념이나 마무리로 간다. 한 세션 안에서 무한 보충·재출제를 하지 않는다.
- paused는 세션 수명 상태이며 현재 개념 단계를 덮어쓰지 않는다. 평가 결과가 정상 도착하면 paused를 유지한 채 복귀할 피드백만 저장한다.
- 마치기는 현재까지의 결과로 completed를 만들며 미수행 항목을 표시한다. abandoned는 학습 취소 이력으로 구분한다. 최종 완료는 성공률과 별개다.
- 종료·삭제 뒤 도착한 모델 응답은 lease/revision 확인으로 진행에 반영하지 않는다. 준비가 끝났다고 삭제한 세션을 다시 생성하지 않는다.

## 6. 자기 설명 평가와 도움

- 평가 결과는 score 하나 대신 기준별 met/missing/contradicted/uncertain과 짧은 피드백을 사용한다.
- 기준마다 학생 답변 구절과 원문 위치를 연결한다. 학생이 쓰지 않은 문장을 인용하거나 존재하지 않는 출처를 반환하면 검증 실패로 처리한다.
- 의미가 맞는 다른 표현을 허용한다. 단순 키워드 포함만으로 이해 판정을 내리지 않는다.
- 도움은 관련 원문, 첫 힌트, 다음 힌트, 모범 설명 순서로 선택 제공한다.
- 충분히 설명했으면 보완을 건너뛰고 확인 문제로 간다. 미확정 평가에서는 원문·자기 점검 후 진행을 허용한다.
- 확인 문제는 서버에서 정답 비교로 채점하고, 제출 뒤에 정답·해설을 공개한다.
- 결과에 설명 수행과 확인 문제 수행을 따로 표시한다. 다음 날 기억 유지·새로운 응용 능력은 미평가로 둔다.

### 6.1 피드백 응답·실패 처리

- 응답은 기준별 criterion_id, status, student_quote(해당 시), source_refs, 짧은 이유와 다음 확인을 포함한다. 서버는 묶음에 없는 기준·출처, 학생 답변에 없는 인용, 누락 기준을 검사한다.
- 채점에는 서버에 고정된 원문·기준·제출 답변을 사용한다. 기존 주관식 API에 클라이언트 모범답안을 보내는 경로를 그대로 재사용하지 않는다.
- 모델 오류·잘린 응답·잘못된 JSON·검증 실패는 평가 오류다. 0점·오답·취약 개념으로 저장하지 않는다.
- 답안은 저장하고 명시적 재시도 또는 자기 점검으로 진행한다. 자기 점검 결과는 self_report로 표시하며 AI 검토 결과로 안내하지 않는다.
- 자기 점검은 준비가 끝난 회상의 평가 실패·uncertain에서만 제공한다. 모범 설명을 열고 이해함/추가 확인/모르겠음 중 선택해 self_check 명령으로 기록한다. 확인 문제의 정오답이나 AI 기준별 판정을 사용자 선택으로 덮어쓰지 않는다.
- 준비 묶음 자체가 실패하면 답변 화면을 만들지 않고 범위 수정·재시도를 제공한다. 실패한 결과를 임의 질문·정답으로 채우지 않는다.

### 6.2 수행 근거 필드

attempt에는 phase, assistance_during_attempt, prior_instruction_in_session, prior_question_exposure, reference_opened, evaluation_method, feedback_version을 구분해 저장한다.

- 보완 뒤 새 확인 문제를 도움 없이 맞힌 결과는 보완 직후 기초 확인이다. 처음부터 알고 있었다거나 장기 기억이 확인됐다는 뜻이 아니다.
- 다른 개념의 보완 원문이 다음 개념의 근거와 겹치면 prior_instruction으로 기록한다.
- 도움 요청은 원문·힌트 내용을 반환하기 전에 저장한다. 새로고침으로 도움 이력이 초기화되지 않는다.
- 앱 밖에서 본 자료·외부 도움을 완벽하게 탐지하지 않는다. 결과의 도움 없음은 앱 내 기록과 사용자 보고 범위의 표현이다.

## 7. 저장 구조

| 테이블 | 주요 내용 |
| --- | --- |
| learning_session_packs | id, user_id, course_id, material_id, source_hash, selected_scope, source_snapshot, source_units, preparation_key, content, content_version, status |
| learning_sessions | id, user_id, course_id, pack_id, familiarity, target_minutes, status, current_item_id, revision, result, created/updated/completed_at |
| learning_session_items | id, session_id, local_concept_id, phase, recall_draft, check_draft, help_state, outcome, quality_report, revision |
| learning_session_attempts | id, item_id, kind, immutable_answer, rubric_result, check_result, assistance, method, prior_exposure, policy_version, created_at |
| learning_session_operations | id, user_id, session_id, command_key, input_hash, kind, status, lease_token, lease_expires_at, attempt_no, response_ref, error_code |

서버가 상태·채점 결과를 저장한다. draft 저장·진행·평가 완료는 revision으로 충돌을 확인하고, 동일 제출의 재시도는 같은 결과를 반환한다. 원문·답변·정답은 비용·일반 로그에 기록하지 않는다.

### 7.1 제약·수명

- 모든 테이블은 사용자 소유 관계를 갖고, 세션·묶음·자료·과목의 소유자가 일치해야 한다. 연결은 서버 검사와 복합 FK/제약으로 검증한다.
- packs는 materials의 실제 키(course_id, id)를 참조한다. 자료 삭제는 해당 묶음·세션·단계·답변·작업을 cascade 삭제한다. 과목 삭제·auth 사용자 삭제도 같은 데이터를 제거한다.
- 준비 키는 사용자·과목 범위에서 고유하다. 같은 묶음의 진행 중 세션을 중복 생성하지 않는 제약을 둔다. 이미 진행 중이면 새 생성 대신 해당 세션을 반환한다.
- command_key는 사용자 범위에서 고유하고 input_hash를 함께 비교한다. 같은 키의 다른 요청은 409로 반환한다. 답변은 단계·제출 회차에 대해 중복 생성하지 않는다.
- 공개 초안과 제출 답변을 분리한다. 제출 후 답변은 immutable이며 모델 평가·재시도가 이를 덮어쓰지 않는다.
- session/item revision과 operation lease는 목적이 다르다. 사용자 초안 충돌에는 item revision, 단계 이동에는 session revision, 지연된 모델 응답 반영에는 lease와 해당 attempt ID를 검사한다. paused 전환만으로 정상 평가가 무조건 폐기되지 않도록 한다.
- 활성 세션 조회 인덱스(user_id, status, updated_at), 하위 데이터 FK 인덱스, 준비 키·command_key 고유 인덱스를 추가한다.
- 기존 데이터 초기화는 materials/courses 삭제로 신규 데이터를 제거할 수 있게 한다. profile.ts의 초기화 성공 후 로컬 초안도 지우며, 새 정리 경로가 삭제한 데이터가 없다고 직접 DB 권한 오류를 내지 않게 한다.
- 참조가 없는 준비 실패·중단 묶음 정리 정책은 관리 명령으로 문서화한다. 예약 실행 시스템을 필수로 추가하지 않는다.

### 7.2 저장 경로·권한 결정

초안의 단순한 서버 저장 표현으로는 정답 보관과 상태 제어가 충분하지 않아 다음 경로로 확정한다.

1. 신규 데이터는 FastAPI API를 통해서만 읽고 쓴다. 프론트가 Supabase에서 packs·attempts를 직접 select/update하지 않는다.
2. 기존 require_api_user로 JWT를 검증하고 새 경로에서는 실제 사용자 ID가 없는 개발용 익명 결과도 거절한다. 요청 body의 user_id는 받지 않는다.
3. 원문 읽기는 사용자 토큰·기존 자료 RLS를 활용한다. 이를 위한 인증 컨텍스트를 새 세션 경로에 한정해 전달한다.
4. 새 데이터의 원자적 명령은 서버 전용 DB 함수(RPC)로 처리한다. 함수는 security invoker를 기본으로 하고 테이블·함수의 public/anon/authenticated 권한을 명시적으로 회수해 service_role만 필요한 접근·실행을 갖게 한다. 기존 테이블·함수의 권한을 일괄 변경하지 않는다.
5. FastAPI에 서버 전용 Supabase secret key를 환경변수로 추가한다. secret key 요청과 사용자 JWT 요청의 httpx 클라이언트·헤더를 분리한다. secret key는 apikey에 사용하고 사용자의 Authorization을 관리자 요청에 섞지 않는다.
6. 서버 권한은 RLS를 우회하므로 repository와 RPC가 검증된 사용자 ID로 소유 관계를 직접 확인한다. ID만으로 임의 행을 읽거나 갱신하지 않는다. 다른 사용자 데이터가 섞이는 경우는 404로 처리한다.
7. 새 5개 테이블에 RLS도 활성화하고 브라우저 역할의 직접 접근·RPC 실행 거부를 DB 테스트로 확인한다. API의 DTO 필터만으로 정답이 보호된다고 간주하지 않는다.
8. 키가 없으면 신규 기능만 unavailable로 반환하고 기존 앱은 작동하게 한다. 추가 배포 설정은 구현 범위에 명시하고 다른 기능의 키·인증 방식을 전면 교체하지 않는다.

공식 근거: [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [함수 권한](https://supabase.com/docs/guides/database/functions), [API 키](https://supabase.com/docs/guides/getting-started/api-keys). 프로젝트의 실제 Data API·역할 설정은 구현 단계에서 테스트 환경으로 확인한다.

## 8. API

| API | 동작 |
| --- | --- |
| POST /learning-sessions | course_id, material_id, scope, familiarity, target_minutes, concept_count로 세션 생성. 준비 중이면 202와 session/operation ID |
| GET /learning-sessions | active/paused/preparing 등 허용 상태와 limit으로 본인 세션 조회 |
| GET /learning-sessions/{id} | 공개 현재 상태·질문·공개가 허용된 과거 결과 |
| GET /learning-sessions/scopes | course_id/material_id로 허용 페이지·제목·문단 범위 조회. 동적 ID 경로보다 먼저 등록 |
| PATCH /learning-sessions/{id}/draft | item_id, expected_item_revision, text 또는 선택 값을 저장 |
| POST /learning-sessions/{id}/answers | item_id, kind, answer, revision으로 제출 고정. 평가 중이면 202 |
| POST /learning-sessions/{id}/help | item_id, help_type으로 원문·힌트·모범 설명 공개와 노출 기록 |
| POST /learning-sessions/{id}/actions | advance/skip/self_check/pause/resume/finish/abandon과 허용된 현재 대상을 검사해 실행 |
| POST /learning-sessions/{id}/operations/{operationId}/retry | 실패·만료 작업만 제한된 횟수로 재시도 |
| POST /learning-sessions/{id}/items/{itemId}/report | 오류 유형·선택 설명으로 문항/피드백 신고, 결과에 확인 필요 표시 |
| GET /learning-sessions/{id}/operations/{operationId} | 준비·평가 처리 상태 조회 |

초안 저장을 제외한 명령 API는 expected_revision과 idempotency_key를 받는다. 학생이 phase·score·정답 여부를 요청해서 직접 확정하지 못하게 한다. 초기 생성은 아직 session revision이 없으므로 idempotency_key와 입력 해시만 검사한다.

서버 경로는 /learning-sessions이며 프론트의 기본 /api 프록시 뒤에서 /api/learning-sessions로 호출한다. idempotency_key는 JSON body에 두고, 별도 출처 호출을 위해 CORS에 PATCH를 추가한다. scopes 응답의 source_hash를 생성 요청에 포함해 원문 변경 시 범위를 다시 확인하게 한다. 서버가 실제 원문 해시를 검증한다.

### 8.1 공개 응답과 오류 계약

- GET은 현재 단계의 공개 질문, 내 초안, 저장 상태, 허용 행동, 이미 공개한 피드백만 반환한다. 미래 질문·기준·정답·미열람 힌트·비공개 원문 스냅샷 전체를 직렬화하지 않는다.
- 비공개 저장 모델과 공개 Pydantic response_model을 분리한다. public_projection으로 단계별 공개 허용 여부를 판단하고 응답 모델로 필드를 제한한다.
- 확인 문항의 answer_index·해설은 제출 뒤 공개한다. 원문·모범 설명을 사용자가 열면 해당 시도의 도움 이력을 먼저 저장한다.
- 오류는 error_code, message, retryable, current_revision(해당 시), operation_id(해당 시)를 제공한다. 기존 parseApiError와 함께 세션 전용 오류 파서를 둔다.
- 401은 재로그인 후 복원, 404는 삭제·접근 불가, 409는 충돌·잘못된 상태, 422는 입력 수정, 429는 실행/예산 한도, 503은 기능·모델 일시 불가로 구분한다. 409/422를 자동 재시도하지 않는다.
- 필드 길이·입력 범위·명령 enum을 서버 스키마로 제한한다. 사용자 요청과 원문 내용이 상태·평가 정책을 바꾸는 명령으로 실행되지 않도록 분리한다.
- 문항·피드백 신고는 본인이 열람한 항목에 대해 허용하고 답변·현재 단계를 바꾸지 않는다. DB·제공자 오류의 원문에 학생 답변·키·SQL 인자가 섞이지 않도록 공개 메시지와 운영 error_code를 정리한다.

## 10. 중단·재개·비용

- 초안은 디바운스 저장하고 제출 전에 최신 답변을 고정한다. 로컬에는 사용자·세션별 미전송 초안을 보관한다.
- 새로고침·기기 재접속은 서버 상태로 복원한다. 서버에 도착하지 않은 로컬 초안은 같은 기기에서 복원한다.
- 평가 중에는 같은 답변을 중복 제출하지 않고 준비·평가 상태를 조회한다.
- 세션 목표 시간은 사용자가 조절할 수 있고, 초과했다고 강제 종료하지 않는다.
- 기본 개념 2개는 준비 1회 + 자기 설명 평가 2회로 LLM 호출 3회를 목표로 한다. 힌트·확인 채점·요약 결과는 저장된 내용과 일반 코드로 처리한다.
- 재시도와 실제 모델 호출 횟수를 기록하고 자동 반복 호출을 제한한다.

### 10.1 초안과 재개

- 600~1000ms 디바운스는 초기 설정안이다. 한글 IME composition 중에는 저장을 미루고 composition 종료·입력 완료에서 저장한다.
- 초안 저장 요청은 항목별로 직렬화한다. 마지막 응답이 오래된 입력을 덮지 않게 클라이언트 sequence와 item revision을 비교한다.
- 제출은 최신 입력을 별도 포함해 서버에서 바로 고정한다. 초안 저장의 마지막 왕복이 누락됐다고 이전 답안을 평가하지 않는다.
- IndexedDB 등 같은 기기 저장소에 사용자·세션·항목별 미전송 초안과 서버 기준 revision을 둔다. 저장 실패는 화면에 표시한다. 계정 전환·로그아웃·초기화에서 해당 사용자 자료를 제거한다.
- 다른 탭의 수정과 충돌하면 서버 최신 상태와 로컬 미전송 초안을 보존해 선택하게 한다. 다른 기기에는 서버 저장분만 복원된다는 점을 구분한다.
- 로컬 초안은 서버에서 세션 존재·소유권 확인 후 복원한다. 삭제된 자료·세션의 초안을 서버에 다시 올려 되살리지 않는다.

### 10.2 모델 작업과 동시성

1. DB 명령이 상태·소유자·revision·command_key를 확인하고 제출 답변·operation을 원자적으로 저장한다.
2. transaction을 닫은 뒤 비동기 모델 호출(ainvoke 등)을 수행한다. 기존 동기 어댑터를 쓰면 스레드풀로 분리해 이벤트 루프를 막지 않는다. 모델 응답을 기다리는 동안 DB 행 잠금을 유지하지 않는다.
3. 결과 검증 후 별도 DB 명령이 operation lease·attempt ID·현재 수명 상태를 확인해 반영한다. 종료·삭제·교체된 작업 결과는 폐기한다.
4. command_key·입력 해시 재전송 검사를 새 revision 검사보다 먼저 수행한다. 같은 키·같은 입력은 이미 revision이 바뀌었어도 진행 중 operation 또는 저장된 결과를 반환하고, 같은 키의 다른 입력은 거절한다.
5. 초기 모델 timeout은 준비 60초·평가 30초, lease는 최대 호출 시간보다 여유 있게 설정하는 안으로 시작한다. 실제 모델·프록시 지연을 보고 조정한다.
6. 모델 처리 중 HTTP 연결이 끊겨도 새로고침은 operation을 조회한다. 서버 작업이 끝났으면 결과를 열고, 프로세스 종료·lease 만료면 retryable로 전환해 명시적으로 재시도한다.
7. 이번 구현은 영속 워커가 아니다. 서버 재시작 후 작업이 자동으로 계속된다고 보장하지 않는다. 만료 판정은 다음 API 조회·재시도에서 할 수 있게 한다.
8. 재시도는 같은 논리 답변에 새로운 attempt_no·lease를 사용한다. 늦은 이전 응답은 반영하지 않는다. 외부 모델의 과금까지 정확히 한 번으로 보장하는 것은 아니며 새 호출이 필요하면 비용에 포함한다.
9. 모델 응답 뒤 DB 저장이 실패하면 살아 있는 요청 안에서 검증한 동일 결과의 저장만 제한적으로 재시도한다. 저장 전 프로세스까지 사라지면 응답은 복원할 수 없으므로 미평가로 남기고 예산 안의 명시적 재평가를 제공한다. DB에는 저장됐고 HTTP 응답만 유실된 경우는 같은 명령 조회로 복원한다.

### 10.3 호출·지연 한도

- 세션별 LLM 호출 상한은 concept_count + 2로 시작한다. 기본 2개는 정상 목표 3회, 실패 복구용 추가 1회까지 총 4회다. 캐시 적중·모르겠어요는 실제 호출을 줄인다.
- 준비·평가에 새 어댑터를 사용해 SDK의 숨은 자동 재시도를 끄거나 동일 예산 안에 계측한다. 이번 기능에서 임의 모델 전환·다중 검증 호출을 추가하지 않는다.
- 한 사용자의 신규 모델 작업은 동시에 1개로 제한한다. 진행 중 작업은 같은 operation을 조회하고, 별도 작업 한도 초과에는 429를 반환한다. 프로세스 메모리 제한만으로 다중 프로세스 전체를 제어했다고 간주하지 않는다.
- DB 예약 명령에서 호출 예산·진행 중 lease를 함께 검사한다. 새로고침·탭 이동이 호출 횟수를 초기화하지 않는다.
- 준비·평가마다 실제 모델 ID, 호출 번호, 시간, 토큰 제공 여부, 성공/실패를 남긴다. 본문·답안·정답은 기록하지 않는다. 전체 서비스 비용 대시보드는 별도 범위다.
- 예산 소진 시 답안·원문·자기 점검·세션 마치기는 계속 제공한다. 자동 반복 대신 확인 필요 상태로 남긴다.

### 12.2 검증 방법과 통과 조건

- Vitest: 현재 node 환경에 맞는 순수 정책·DTO·초안 순서 테스트. 기존 설정이 React DOM 테스트를 제공한다고 가정하지 않는다.
- pytest: 모델·repository를 가짜로 둔 API·경계 테스트와, 실제 Postgres의 원자적 함수·제약·권한·동시성 테스트를 구분한다.
- DB 통합 검증 환경을 신규 PR 범위에 포함한다. CI Postgres 서비스와 테스트용 DB 드라이버를 추가하고 auth 역할·courses/materials의 최소 fixture로 신규 migration을 검사한다. 실제 Supabase 테스트 환경에서는 Data API 권한까지 확인한다. 가짜 repository만으로 RLS·RPC가 검증됐다고 보고하지 않는다.
- fixture는 일반 개념 텍스트, 페이지가 있는 자료, 긴 무마커 자료, 수식·코드 포함 텍스트, 불확실 OCR, 단일 개념 자료의 6종부터 준비한다. 거절해야 할 입력도 포함한다.
- 피드백은 올바른 다른 표현·필수 조건 누락·인과 역전·빈 답변·무관 답변·잘못된 인용·uncertain을 포함한 사람이 기준을 붙인 사례로 검사한다.
- 실제 LLM 평가는 선택한 소수 자료·횟수·호출 한도에서 별도로 실행한다. 결과 품질은 사람의 원문 검토와 함께 기록한다.
- 내부 파일럿에서는 시작 부담, 첫 답변까지 시간, 회상·보완·확인 단계 이탈, 재개 성공, 피드백 오류 신고를 관찰한다. 세션 완주율만으로 기억 향상을 결론내리지 않는다.
- 출시 전 T07~T18의 권한·중복·복구·삭제 차단 결함은 0건이어야 한다. 나머지 필수 동선도 통과하고, 콘텐츠 오류·미확정의 처리 경로를 확인한다.
- 기존 typecheck·lint·Vitest·pytest·build와 자료·퀴즈 주요 동선에 회귀가 없어야 한다.

## 13. 자체 검토

별도 검토 문서 learning-session-plan-review.md에 10개 발견 사항과 반영 위치를 기록했다. 핵심 수정은 다음과 같다.

1. 개념 그래프·검색·자동 복습을 선행 조건에서 제거하고 세션 원문·로컬 개념만 사용한다.
2. API DTO뿐 아니라 DB 직접 접근·함수 권한·서버 소유 관계 검사까지 정의한다.
3. 모델 요청을 DB transaction 밖으로 분리하고 operation lease·만료·명시적 복구를 정의한다.
4. 도움·이전 학습·같은 문항 재노출을 구분하고 객관식 한 문제의 결과를 장기 이해로 확대하지 않는다.
5. 자료 변경·삭제·계정 초기화, 한글 초안·복수 탭·응답 유실, SDK 재시도·호출 예산을 테스트 범위에 넣는다.

검토 결론은 좁은 첫 세션 구현을 시작할 수 있을 정도로 계획 경계와 주요 예외를 구체화했다는 것이다. 구현의 안전성·학습 효과가 검증됐다는 뜻은 아니다. DB 권한·운영 timeout·실제 콘텐츠 사실성은 구현·파일럿에서 확인할 남은 항목이다.
