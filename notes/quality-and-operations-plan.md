# Tongkk 정확도·요약 재사용·운영 개선 실행 계획

작성일: 2026-11-19 / 코드 확인 기준: main, 4488bd5

이 문서는 요청한 10개 항목의 구현 계획이다. 아래 API·테이블·파일 이름은 추가 개발안이며, 현재 구현된 것으로 간주하지 않는다.

## 목표와 1차 범위

- 주관식 점수와 정답 표시가 모순되지 않는다.
- 같은 조건의 요약은 다시 생성하지 않고 저장된 결과를 연다.
- 다른 페이지·추가 지시·원문의 요약을 서로 덮어쓰지 않는다.
- 요약의 구조적 문제를 표시하고, AI 품질과 비용을 측정한다.
- 문서 변환 부하를 제한하고 서버 실행 환경을 재현한다.
- 자료 관리 화면을 기능별로 분리하고 정보 위계를 정돈한다.

서버 작업 큐, 탭을 닫은 뒤의 생성 지속, 부분 재요약, 의미 검증용 추가 LLM, 학습 계획·FSRS·검색 튜터는 이번 10개 항목과 별도 범위다. 특히 이번 동시 실행 제한은 영속 작업 큐를 구현하는 작업이 아니다.

## 1. P0 — 주관식 점수와 정답 판정 통일

### 결정할 동작

- 현재 기준인 70점 이상 정답을 유지한다.
- 정상적인 유한 숫자 점수를 0~100의 정수로 정규화한 뒤 정답 여부를 계산한다. 예: 반올림 후 70점이면 정답.
- AI의 is_correct는 최종 판정에 사용하지 않는다. AI의 역할은 점수·피드백·모범답안 제안이다.
- 점수 누락·문자열·boolean·비정상 숫자는 채점 실패로 처리한다. 오류를 학생의 0점 답안으로 저장하지 않는다.
- 문항의 주관식 점수와 퀴즈 전체 정답률은 다른 지표다. 이번 작업에서 전체 결과를 부분점수 평균으로 바꾸지 않는다.

### 구현 작업

1. 서버에 점수 정규화·정답 계산 함수를 만들고 /quiz/grade-subjective에서 사용한다.
2. 프롬프트의 출력 계약을 점수 중심으로 조정하되 API 응답의 is_correct는 서버가 계산해 계속 제공한다.
3. src/services/gpt.ts도 점수에서 isCorrect를 계산하도록 맞추고 잘못된 응답은 에러로 반환한다.
4. Quiz.tsx의 배지, 해설, 결과 정답 수, 오답 목록, quiz_attempts 저장이 동일한 판정을 사용하는지 확인한다.
5. 신규 답안 JSON에 gradingPolicyVersion을 기록한다. 과거 기록의 저장된 점수·정답 수는 자동 재계산하지 않는다. 과거 결과 복원과 신규 채점을 구분한다.

### 파일

- 수정: server/main.py, server/llm.py 또는 신규 server/grading.py, src/services/gpt.ts, src/pages/Quiz.tsx.
- 확인: src/services/quizAttempts.ts, src/pages/ReviewNotes.tsx.
- 테스트: server/tests/test_subjective_grading.py, src/services/subjectiveGrading.test.ts 등.

### 검증과 완료 기준

- 69점/70점, 반올림 경계, 음수/100 초과, 잘못된 타입을 검사한다.
- AI가 90점·오답 또는 30점·정답을 반환해도 서버·화면·저장이 점수를 따른다.
- 실패한 채점은 미채점 상태로 남고 재시도할 수 있다.
- 객관식·OX·단답형과 기존 결과 복원 동작은 회귀 확인한다.

규모: 작음. DB 테이블 변경 없이 답안 JSON 확장으로 처리 가능.

## 2. P0 — 요약 저장·중복 판정 기준 수정

### 요청 동일성 정책

같은 요청인지 판단하는 정규화된 메타데이터를 만들고, 이를 직렬화한 값의 SHA-256을 request_key로 사용한다.

| 포함 정보 | 처리 정책 |
| --- | --- |
| 자료와 순서 | 실제 원문 합본에 사용된 자료 ID·이름·순서를 기록. 순서가 출력에 영향을 주면 키에도 반영 |
| 원문 해시 | 파일명·파일 크기 대신 실제 생성에 사용하는 원문 내용으로 계산. 페이지 마커·수식·코드의 의미를 유지 |
| 페이지 선택 | 빈 값은 전체. 1-3과 3,1,2는 동일하게 정규화. 실제 마커를 기준으로 검증 |
| 추가 지시 | 앞뒤 공백·줄바꿈 방식만 정규화. 문장 내부 공백·대소문자 등을 과하게 없애지 않음 |
| 템플릿 | GENERAL, LECTURE_NOTE, MINDMAP, CHEAT_SHEET 구분 |
| 생성 설정 | GPT/Gemini 별칭뿐 아니라 실제 모델 ID, 프롬프트 버전, 입력 처리·구간 분할 버전 포함 |

해시가 같아도 조회는 반드시 로그인 사용자와 과목 범위에서 수행한다. 키가 권한 검사를 대신하지 않는다.

### 구현 작업

1. 페이지 범위와 실제 입력을 정규화하는 계약을 정한다. 다중 자료의 동일한 페이지 번호는 자료별로 구분해 출처 맵에 기록한다.
2. 페이지가 없는 자료에서 범위를 무시하는 현 동작을 명시적으로 안내한다. 잘못된 범위·존재하지 않는 페이지만 선택한 입력은 생성 전에 오류로 반환한다.
3. 서버에 AI 호출 없는 POST /summaries/prepare를 추가하는 안으로 진행한다. 입력·설정을 검증하고 정규화된 메타데이터, source_hash, request_key, 실제 모델·버전을 반환한다.
4. 프론트의 합본·구간 분할과 서버 준비 단계가 같은 입력을 해석하도록 공유 fixture로 검증한다. 준비 이후 모델·처리 버전이 달라지면 재준비를 요구한다.
5. SavedSummary와 DB에 request_key, source_hash, generation_config(JSON), 생성 메타데이터를 추가한다. generation_config에는 자료별 해시·순서·페이지 범위·추가 지시·실제 모델·버전을 보존한다.
6. unique(course_id, template, material_ids)를 제거하고 사용자·과목·요청 키·생성 시각의 조회 인덱스를 만든다.
7. 저장은 자료·템플릿 기준 업데이트에서 신규 결과 ID 기준으로 변경한다. 다른 조건과 명시적 재생성은 새 행을 만들며, 같은 생성의 저장 재시도는 같은 ID로 처리한다.
8. 과거 요약은 request_key를 null로 유지한다. 과거 페이지 범위·지시를 추정해 키를 만들거나 자동 재사용하지 않는다.
9. 요약 열기에서 저장된 페이지 범위·자료 순서·추가 지시를 복원하고 튜터에도 전달한다. 현재 원문 해시가 다르면 원문 변경을 알리고 과거 요약과 현재 원문을 같은 근거로 취급하지 않는다.
10. 요약 삭제·자료 삭제·과목 삭제·계정 초기화 시 여러 조건·여러 버전이 함께 정리되는지 확인한다.

### 이력 정책

- 명시적 재생성은 새 summary ID를 사용한다. 기존 요약과 해당 요약의 튜터 대화를 유지한다.
- 목록은 요청 조건별 최신 결과를 우선 보여주고 이전 결과는 선택해서 열 수 있게 한다.
- 기존 요약은 이전 기록으로 계속 열 수 있다. 원문이 변경된 이전 기록의 정확한 원문 복원이 필요하면 원문 스냅샷 저장을 후속 범위로 추가한다.
- 메타데이터 없는 이전 기록은 자동 재사용 대상에서 제외하되, 사용자가 직접 열 수는 있다.

### 파일·DB

- 수정: supabase/schema.sql, src/services/summaries.ts, src/services/materials.ts, src/services/gpt.ts, src/services/summaryStream.ts, server/schemas.py, server/main.py, server/prompts.py.
- 신규: supabase/migrations/의 버전 SQL, src/services/summaryIdentity.ts, server/summary_identity.py.
- UI 연결: src/pages/Summary.tsx 또는 분리된 생성 훅·설정 컴포넌트.
- DB 변경은 기존 데이터에 nullable 컬럼·인덱스를 추가하는 단계와 기존 고유 제약을 제거하는 단계를 나눈다.

### 검증과 완료 기준

- 같은 조건과 동등한 페이지 표기는 같은 키가 된다.
- 원문·범위·지시·템플릿·실제 모델·프롬프트 버전 변경은 다른 키가 된다.
- 같은 파일명·같은 크기의 다른 원문도 구분한다. 현재 material ID가 파일명:크기여서 이를 원문 해시로 대체할 수 없다.
- 다른 조건의 요약이 공존하고, 재생성 후 이전 대화가 새 결과에 섞이지 않는다.
- 마이그레이션 전후 기존 요약·튜터 대화 개수가 보존된다. 실제 DB의 RLS가 새 조회·저장에도 적용된다.

규모: 큼. 재사용·검증·사용량 집계의 공통 기반.

## 3. P0 — 동일 조건의 요약 재사용

### 사용자 흐름

설정 입력 → 준비·동일 조건 조회 → 기존 결과가 있으면 바로 열기 → 없으면 생성 → 검증 → 저장.

기존 결과 화면에 새로 생성하기를 별도 행동으로 제공한다. 현재 설정 화면의 중복 확인 모달은 이 흐름에 맞춰 정리한다.

### 구현 작업

1. 요약 목록 전체의 자료·템플릿 비교 대신 request_key로 정확히 조회한다. 최신 후보의 메타데이터를 먼저 받고 선택된 본문만 조회한다.
2. 설정 화면, 템플릿 카드, 자료 상세에서 시작하는 경로를 공통 생성 함수로 연결한다.
3. 재생성 버튼은 재사용 조회를 건너뛰고 같은 조건의 새 결과를 생성한다.
4. 실패·중단·빈 결과·저장 실패 상태를 구분한다. 저장이 끝난 완성 결과만 자동 재사용한다. 검증 경고는 표시하면서 열 수 있고, 구조적으로 열 수 없는 결과는 제외한다.
5. 동일 탭에서는 요청 키별 진행 Promise를 공유하고 연속 클릭을 막는다.
6. 생성 성공 후 저장만 실패하면 본문을 유지하고 저장만 재시도한다. LLM을 다시 호출하지 않는다.
7. 목록·개수 캐시를 갱신하고 조건·생성 시각·이전 결과를 표시한다.

### 동시 요청의 범위

1차는 저장된 결과 재사용과 동일 탭 중복 실행 방지까지다. 서로 다른 탭·서버에서 동시에 캐시 미스가 나면 AI 호출이 중복될 수 있다. 이를 완전히 막으려면 서버의 원자적 생성 예약·만료·결과 저장이 필요하며, 영속 작업 시스템 단계로 분리한다. 단순한 버튼 잠금을 서버 전체의 중복 방지로 설명하지 않는다.

### 검증과 완료 기준

- 같은 조건으로 두 번째 접근하면 추가 LLM 호출이 0회다. 준비·DB 조회는 발생할 수 있다.
- 다른 페이지·지시·원문이면 새로 생성한다.
- 기존 보기·재생성·생성 실패·저장 재시도·다른 진입 경로를 확인한다.
- 기존 결과를 열 때 범위와 튜터 문맥이 복원된다.

규모: 중간. 2번 완료 후 진행.

## 4. P1 — 요약 결과 검증기

### 검증 계약

검증기는 사실성 보증이 아니라 코드로 확인 가능한 문제를 찾는 장치다. 원문·출처가 없으면 통과가 아니라 검증 불가로 기록한다.

보고서에는 validator_version, 검사별 code·severity·메시지·문단 위치·자료/페이지, 전체 상태(pass/warning/error/unverifiable), 검사 시각을 저장한다.

### 구현 작업

1. 일반 요약·강의 노트·치트시트의 Markdown을 문단·제목·표·코드·수식 단위로 나눈다.
2. 긴 문단의 완전 중복과 유사 문단 후보를 찾는다. 수식·코드·표·짧은 용어·정상적인 반복 제목은 중복 경고의 예외로 다룬다.
3. 미완성 코드 펜스·수식 구분자, 비정상적으로 반복되는 최상위 제목, 템플릿별 필수 구조를 검사한다.
4. 마인드맵은 Markdown 검사 대신 JSON 파싱, 노드 스키마, 빈 노드·잘못된 관계를 검사한다.
5. 출처 표현을 현재 렌더러와 같은 규칙으로 파싱한다. 자료명, 해당 자료의 실제 페이지/슬라이드, 선택 범위와 대조한다. 다중 자료에서 파일명 없는 p.3은 특정 자료로 단정하지 않는다.
6. 전체 구간이 합쳐진 뒤 1회 검사한다. 구간별 정상 결과도 병합 후 중복될 수 있다.
7. 요약별 validation_report와 validation_version을 저장한다. 재사용 시 버전이 오래됐으면 AI 없이 재검사한다.
8. 결과에 확인할 항목과 해당 문단·원문으로 이동하는 동작을 제공한다. 원문 위치가 없으면 이동 가능하다고 표시하지 않는다.
9. 원본 결과는 유지한다. 유사 문단이나 출처를 자동 삭제·수정하지 않는다. 구조 오류는 완료 결과 저장·자동 재사용을 막고, 경고는 결과를 보여주면서 안내한다.

### 파일

- 신규: src/services/summaryValidation.ts와 테스트, 결과 보고서 UI.
- 연계: 분리된 Markdown·출처 파서, summaryStream.ts 호출 완료 지점, summaries.ts, mindmapData.ts, supabase/schema.sql.
- 현재 생성·저장을 프론트가 담당하므로 1차도 프론트에서 검사한다. 서버 작업으로 옮길 때 서버에서 동일 fixture를 통과하는 검증을 적용한다.

### 검증과 완료 기준

- 의도적으로 넣은 반복 문단·미완성 블록·범위 밖 페이지·없는 자료명을 검출한다.
- 정상적인 수식·코드·표·여러 자료의 같은 페이지 번호를 오탐하지 않는지 고정 사례로 확인한다.
- 텍스트·이미지 자료에서 검사 가능한 범위와 불가능한 범위를 구분한다.
- LLM 호출 없이 검사·저장·재검사가 가능하다.

규모: 중간~큼. 출처 파서 분리와 2번 메타데이터 필요.

## 6. P1 — AI 사용량·비용 기록

### 기록 단위

사용자가 시작한 작업(root operation)과 실제 외부 모델 호출(attempt)을 구분한다. 긴 요약의 여러 구간, 재시도, 튜터 도구 호출 뒤 추가 응답을 각각 실제 호출로 기록한다. 외부 호출 비용은 attempt의 합계로 계산해 상위 요청과 이중 집계하지 않는다.

| 필드 | 예시·의미 |
| --- | --- |
| operation_id / call_id / parent_call_id | 요약 한 건, 개별 구간·재시도·튜터 호출 연결 |
| feature / provider / model | summary, quiz, grading, tutor, study_plan, wrong_analysis, vision / 실제 모델 ID |
| user_id / course_id / request_key | 인증 사용자·과목·요약 조건 연결, 값이 없는 경로는 null |
| status / error_type | 성공, 제공자 실패, 취소, 응답 파싱 실패 등 |
| input/output/cached tokens | 제공자 실제 usage 값. 미제공은 null과 누락 사유로 기록 |
| estimated_cost / currency / price_version | 당시 모델별 요율로 계산한 추정치와 단가 버전 |
| duration_ms / retry_index | 호출 시간·재시도 번호 |
| cache_hit / generation_id | 재사용과 생성 결과 연결 |

### 구현 작업

1. 요청 컨텍스트와 구조화 JSON 로그를 공통 모듈로 만든다.
2. server/llm.py의 공통 래퍼뿐 아니라 /summarize/stream, server/agent.py의 그래프 내부 호출, _build_visual_llm 경로도 계측한다.
3. 제공자 usage 형식 차이를 정규화한다. 스트리밍 usage가 증분인지 누적인지 구분해서 마지막 집계 값을 중복 합산하지 않는다.
4. 모델 호출이 성공했으나 JSON 파싱이 실패한 경우에도 호출 비용을 남긴다. 취소·오류의 미확인 토큰을 0으로 확정하지 않는다.
5. 요율 표는 모델별·버전별로 관리한다. 실제 적용 시 공식 단가를 확인하며, 모델을 찾지 못하면 비용 미상으로 표시한다. 추론 토큰과 출력 토큰의 중복 계산을 피한다.
6. 캐시 재사용은 모델 호출과 구분해 작업 이벤트에 기록한다. 준비 API 호출을 AI 호출로 세지 않는다.
7. 운영 조회용 ai_call_logs와 ai_operation_logs 테이블을 추가하는 안으로 진행한다. 서버 전용 쓰기 경로·권한을 두고 프론트가 비용·사용자 ID를 조작해 기록하지 못하게 한다.
8. 처음에는 기능·모델·날짜별 SQL 집계와 CSV/JSON 보고서까지 만든다. 별도 관리자 대시보드는 후속 범위다.
9. 강의 원문·학생 답안·이미지·API 키는 비용 로그에 저장하지 않는다. 기록 실패는 본 기능의 실패로 전파하지 않고, 누락 수를 관측한다.
10. 로그 보관 기간과 조회 인덱스를 정하고 대량 기록으로 DB가 무제한 증가하지 않게 정리 절차를 둔다.

### 검증과 완료 기준

- 비스트리밍·스트리밍·비전·튜터 다중 호출·재시도 경로의 호출 수가 맞는다.
- 모델별 토큰·단가 fixture로 계산과 미상 처리를 검증한다.
- 날짜·기능·모델별 실패율, 지연 분포, 추정 비용, 재사용 횟수를 조회한다.
- 추정 비용은 청구서·남은 크레딧과 다른 값임을 보고서에 표시한다.

규모: 큼. 모든 호출 경로에 적용하는 부분이 핵심.

## 8. P1 — 문서 변환 동시 실행 제한

### 기본 정책

초기 동시 실행 수는 보수적으로 1개부터 측정하고 설정으로 조절한다. /convert와 /preview/pdf가 같은 프로세스 내 공통 제한을 공유한다. 캐시 적중과 이미 PDF인 미리보기의 단순 반환은 무거운 변환 슬롯을 사용하지 않는다.

### 구현 작업

1. server/conversion_runtime.py 같은 공통 실행 계층을 만든다. 동시 실행 수·최대 대기 수·대기 제한 시간을 환경변수로 설정한다.
2. 캐시 조회 → 제한된 대기 → 슬롯 획득 → 캐시 재확인 → 실제 변환 → 결과 저장 순서로 연결한다.
3. 대기열이 가득 차거나 대기 시간이 지나면 서버 사용 중 응답과 Retry-After를 보낸다. 프론트는 재시도 안내를 표시하고 무한 재시도하지 않는다.
4. PDF 파싱·OCR·LibreOffice 등 CPU/메모리 작업을 슬롯 안에서 실행한다. 변환 안의 비전 API 대기로 슬롯을 오래 점유하면 해당 단계의 시간도 따로 기록하고 이후 분리 근거로 삼는다.
5. 외부 요청 취소나 비동기 timeout만으로 실행 중인 스레드가 종료된다고 간주하지 않는다. 실제 변환·자식 프로세스 종료가 확인된 뒤 슬롯을 반환하도록 실행 수명을 관리한다.
6. LibreOffice 실행마다 독립된 임시 사용자 프로필을 사용하고, subprocess timeout·실패·임시 파일 정리를 보장한다.
7. 작업 ID, 형식, 캐시 적중, 대기 시간, 실행 시간, 성공/실패, 실패 유형을 구조화 로그에 남긴다.
8. uvicorn 프로세스 수를 배포 문서에 고정한다. asyncio.Semaphore는 프로세스별이므로 여러 worker에서 전체 1개 제한이 되지 않음을 명시한다. 초기 단일 프로세스 범위에서 검증한다.
9. 두 엔드포인트 혼합 부하와 튜터 요청을 함께 실행해 실제 CPU·메모리·대기 시간·응답 지연을 측정한다.

### 검증과 완료 기준

- 혼합 변환 요청의 실제 동시 작업 수가 설정값을 넘지 않는다.
- 실패·시간 초과·요청 취소 이후 슬롯이 누수되거나 너무 일찍 풀리지 않는다.
- 캐시 적중은 변환 대기를 거치지 않고 반환된다.
- 대기와 변환 실패를 구분해 집계할 수 있다.
- 튜터 지연 개선 여부는 측정 결과로 보고하며, semaphore만으로 자원 격리가 완성됐다고 보장하지 않는다.

규모: 중간. 시스템 도구·스레드·취소 수명 처리에 주의.

구조는 책임 경계의 제안이다. 파일 개수를 목표로 삼지 않고 독립적으로 이해·변경할 수 있는 단위만 분리한다.

### 단계별 작업

1. P0 전에 최소 분리: 공통 타입, 원문·페이지·출처 파서, 생성 요청 구성과 저장 흐름을 추출한다.
2. Markdown 보정·출처 이동·수식 정규화 등 순수 함수를 summaryMarkdown.ts로 옮긴다. 화면·복사·PDF가 같은 결과를 쓰게 한다.
3. 업로드·자료 목록·설정·결과·자료 상세를 JSX 단위로 옮긴다. 이름·props를 정리하되 이 단계에서 화면 디자인을 바꾸지 않는다.
4. 비동기 로딩·생성·재시도·저장·에러 상태를 전용 훅으로 이동한다. 여러 boolean 대신 idle/checking/generating/validating/saving/success/error 같은 상태와 해당 데이터를 묶어 관리한다.
5. 과목·자료 변경 뒤 늦은 응답이 다른 화면을 덮지 않게 요청 ID와 현재 대상 확인을 둔다.
6. 화면 구독 해제와 생성 작업 취소를 구분한다. 현재 SPA 이동 뒤 생성 완료·저장이 이어지는 동작을 유지하고, 탭 종료 후 지속까지 보장하지 않는다.
7. PDF·PPT 미리보기와 object URL 정리를 useDocumentPreview로 묶고, 튜터 분할 드래그를 useTutorSplit로 이동한다.
8. 주소·딥링크·선택 복원은 useSummaryRouteState로 분리한다. 한 번의 사용자 이동에 중복 로드가 일어나지 않는지 확인한다.
9. 페이지는 로그인·과목 확인, 화면 조합, 이동 연결 위주로 남긴다. 사용처·타입 정리가 끝난 중복 코드만 삭제한다.

Custom Hook은 화면에서 쓰던 useState/useEffect와 비동기 제어를 이름 있는 함수로 묶는 것이다. 서버로 코드를 옮기거나 AI 에이전트를 추가한다는 뜻은 아니다.

### 검증과 완료 기준

- 업로드·중복 파일·삭제·4개 템플릿·기존 요약 열기·재생성·스트림 실패·저장 재시도를 확인한다.
- 튜터 드래그 질문·분할/확대·원본 미리보기·복사/PDF·퀴즈 이동·딥링크 복원을 확인한다.
- 순수 함수와 비동기 경계에 필요한 테스트를 추가하고, 단순 파일 이동을 재현하는 테스트는 만들지 않는다.
- typecheck·lint·기존 테스트·빌드가 통과한다. 화면은 변경 전과 비교해 회귀 확인한다.

규모: 큼. 최소 추출과 나머지 이동을 별도 PR로 나누는 것이 적절.

## 10. P1 — UI 정리

### 범위와 원칙

1차 화면은 자료 목록·자료 상세·요약 설정·결과다. 대시보드·퀴즈의 같은 패턴은 이 화면에서 확정한 규칙을 다음 PR로 적용한다. 전체 페이지를 한꺼번에 재설계하지 않는다.

### 구현 작업

1. 현재 카드·필터·탭을 목록화하고 유지/통합/카드 제거를 정한다. 단순 정보 구분용 박스 안의 박스를 우선 정리한다.
2. 핵심 행동(자료 추가, 요약 생성), 선택 가능한 자료 항목, 중요 결과는 카드로 유지한다.
3. 자료명·범위·생성일 등 보조 정보는 제목·설명·메타데이터 행으로 묶는다. 그룹 간 여백과 제목 크기·굵기로 구분한다.
4. 화면별 주요 버튼의 강조를 정리하고 보조 행동·삭제 행동을 같은 강도로 표시하지 않는다.
5. 단일 선택 카테고리 탐색은 언더라인 스타일로 바꾼다. 다중 선택, 난이도 선택, 입력용 태그는 의미가 달라 일괄 변경하지 않는다. 현재 실제 적용 대상을 먼저 확정한다.
6. 실제 패널 전환은 tablist/tab/tabpanel 의미와 키보드 이동을 적용한다. 목록 필터는 버튼 그룹·선택 상태를 유지하면서 시각 스타일을 맞춘다.
7. 기존 index.css 디자인 토큰으로 색·간격·테두리·포커스를 맞춘다. 새 인라인 hex를 늘리지 않는다.
8. 좁은 화면의 탭 넘침, 긴 자료명, 많은 요약 조건, 로딩·빈 상태·실패·검증 경고를 조정한다.
9. 라이트·다크 모드와 모바일·데스크톱에서 주요 동선을 시각 비교한다. UI 변경을 위한 별도 단위 테스트 대신 실제 동선·키보드·레이아웃을 검증한다.

### 완료 기준

- 중요 정보와 주요 행동이 먼저 보이고 중복 테두리·카드가 줄어든다.
- 카드 제거로 선택 가능 여부나 클릭 영역이 모호해지지 않는다.
- 단일 카테고리의 언더라인 상태·포커스가 명확하고, 기존 다중 선택은 계속 작동한다.
- 원본/PDF/튜터·요약 생성·재사용 기능이 같은 동선으로 작동한다.

규모: 중간. 디자인 패턴 확정 후 적용 화면 수에 따라 증가.

## DB·배포 적용 순서

1. 실제 스키마·제약·RLS와 기존 요약 수·대화 수를 확인하고 마이그레이션을 준비한다.
2. nullable 메타데이터 컬럼·새 인덱스·관측 테이블을 먼저 추가한다. 기존 클라이언트가 계속 동작하는 단계로 배포한다.
3. 서버의 준비 API·새 응답·관측을 배포한다.
4. 기존 고유 제약을 제거하고 새 저장 모델을 켠다. 구버전 프론트는 자료·템플릿 기준으로 임의의 행을 업데이트하므로, 전환 시 구버전 클라이언트의 새 저장을 차단하거나 새로고침을 요구하는 호환성 게이트가 필요하다.
5. 새 프론트에서 조건 분리·재사용·여러 버전·튜터 문맥을 확인한 뒤 일반 사용으로 전환한다.
6. 잘못된 저장이 발견되면 새 생성·저장을 일시 중지하고 수정한다. 새 조건의 행이 생긴 뒤 옛 고유 제약을 단순 복원하거나 옛 저장 코드로 돌아가지 않는다. 생성된 결과·대화를 보존한 전진 수정 계획을 둔다.

## 검증 운영

- 프론트: npx tsc --noEmit -p tsconfig.app.json, npm run lint, npm test, npm run build.
- 백엔드: server 디렉터리에서 python -m pytest -q.
- DB 변경: 테스트 환경에서 이전 스키마→마이그레이션→기존·신규 데이터 조회/저장/삭제·권한 확인.
- Docker·변환 변경: 실제 시스템 도구를 쓰는 smoke test와 제한된 동시 요청 실험.
- AI 평가: 모의 응답 검증은 CI, 실제 모델 평가는 별도 명시 실행과 비용 상한.
- UI·분리: 주요 동선과 반응형·다크 모드를 확인하고, 새로운 변경이나 실패가 없으면 같은 검사를 반복 확대하지 않는다.
