# 학습 세션 구현 계획 자체 검토

검토일: 2026-11-19 / 대상: learning-session-implementation-plan.md 초안 → 1.0

같은 작성자가 초안을 다시 읽고 현재 저장소·실패 시나리오·학습 판정의 의미와 대조했다. 별도 에이전트에 위임하지 않았다. 코드 리뷰·프로덕션 테스트 결과가 아니라 구현 계획 검토다.

## 1. 검토 방법

1. 앞선 새 기능 계획에서 학습 세션에 꼭 필요한 범위만 남기는지 확인했다.
2. App.tsx, Summary/Quiz 타입·서비스, PdfViewer, backend.ts, server/auth.py, profile/courses 삭제, Vitest·CI 설정을 읽고 재사용 가능 여부를 대조했다.
3. 다른 사용자 접근·직접 DB 조회·동시 제출·중간 저장 실패·프로세스 종료·원문 변경·삭제·모델 오답을 가정해 계획의 빈 부분을 확인했다.
4. 보완 후 정답·자기 점검·같은 문제 재학습이 이해·응용·기억 유지로 잘못 확대되지 않는지 검토했다.
5. Supabase의 공식 RLS·함수 권한·API 키 문서를 확인해 서버 저장 경로의 권한 가정을 수정했다.
6. 발견 사항을 최종 계획에 반영한 뒤 문서의 상태·API·테스트·범위가 서로 맞는지 다시 점검했다.

## 3. 기존 코드와 대조한 구체적인 경계

- PdfViewer는 현재 페이지 이동용 prop이 없다. 첫 버전은 텍스트 근거를 펼쳐 보여주며 PDF 페이지 점프를 숨은 필수 작업으로 넣지 않았다.
- 기존 QuizQuestion에는 정답·해설이 함께 포함되고 question_id가 없다. 기존 객체를 프론트의 세션 DTO로 그대로 재사용하지 않는다.
- 기존 주관식 API는 클라이언트가 모범답안·원문을 보낸다. 새 세션은 서버에 고정된 묶음으로 채점한다.
- FastAPI에는 인증 검증은 있으나 서버 DB 저장 계층이 없다. repository·원자적 함수·서버 전용 설정을 실제 작업에 포함했다.
- materials의 PK는 course_id와 id다. 단일 material_id만 참조하는 FK로 계획하지 않았다.
- profile.ts의 데이터 초기화와 courses.ts의 과목 삭제가 이미 존재한다. 새 데이터가 cascade로 제거되는지와 로컬 초안 제거를 검증한다.
- 기존 Vitest는 node 환경과 .test.ts를 사용한다. React UI 통합 검증이 자동으로 제공된다고 가정하지 않았다.

## 4. 반영 후 시나리오 재검토

| 상황 | 계획에서의 처리 | 추가 확인할 점 |
| --- | --- | --- |
| 같은 답안 두 번 제출 | command_key·입력 해시·원자적 예약으로 같은 작업 참조 | 실제 DB 병렬 테스트 |
| 제출 직후 네트워크 끊김 | 새 답변을 만들지 않고 저장된 operation 조회 | 프록시·브라우저 통합 확인 |
| 모델 호출 뒤 서버 종료 | lease 만료 후 제한된 명시적 재시도 | 외부 호출은 재과금될 수 있음 |
| pause 뒤 정상 평가 완료 | paused 유지·피드백만 저장 | session revision과 lease 충돌 검사 |
| finish·자료 삭제 뒤 늦은 응답 | 결과 반영 거절·부활 금지 | cascade·종료 transaction 검사 |
| 평가 실패 | 제출 답안 유지·미평가·자기 점검 | 에러를 오답으로 집계하지 않음 |
| 캐시된 확인 문제 다시 정답 | 반복·기존 노출로 기록 | 새로운 독립 성공으로 표시하지 않음 |
| 첫 개념 보완이 둘째 개념 내용을 노출 | 공유 원문 단위 기준으로 prior_instruction 표시 | 자기 보고와 앱 내 기록의 한계 표시 |
| 한글 입력 중 자동 저장·로그아웃 | 조합 종료 저장·사용자별 초안 정리 | 실제 브라우저/IME 검사 |
| 원문에 개념 하나만 있음 | 개념 하나 세션으로 축소 | LLM이 임의로 두 번째 개념 추가하지 않는지 검토 |

## 5. 아직 검증하지 못한 항목

1. 운영 Supabase의 현재 테이블·역할·키·Data API 설정은 조회하지 않았다. 신규 권한·함수 테스트는 구현 시 수행해야 한다.
2. 실제 서버의 모델 응답 시간·프록시 제한·작업 프로세스 수를 계측하지 않았다. 문서의 60/30초 timeout·lease·12,000자 입력 상한은 초기 설정안이다.
3. 원문·정답·자기 설명 평가의 사실성은 실제 파일럿 자료와 사람 기준으로 확인해야 한다. 형식·출처 위치만으로 해결되지 않는다.
4. 15분·개념 2개가 학생에게 적절한지는 사용성 검증 전이다. 첫 답변·이탈·재개·부담을 보고 조정한다.
5. 첫 세션은 장기 기억·전이 효과를 검증하지 않는다. 관련 결과를 표시하려면 별도의 지연·응용 평가가 필요하다.

이 항목들은 계획상의 미확인 값과 제품 한계다. 계획 문서만으로 통과했다고 처리하지 않는다.

## 6. 검토 결론

판정: 제한된 학습 세션의 구현에 착수할 수 있는 계획으로 수정했다. 첫 PR은 모의 학습 묶음으로 사용자 흐름·상태·공개 응답을 확인하고, 실제 노출은 DB 저장·권한·실패 복구가 갖춰진 뒤 진행한다.

검토 후에도 가장 중요한 검증 대상은 실제 DB의 권한·원자성, 모델 생성 콘텐츠의 사실성, 학생의 입력 부담이다. 이 세 가지는 구현·파일럿 결과를 받아 다시 판단한다.

공식 문서 확인: [RLS와 서버 권한](https://supabase.com/docs/guides/database/postgres/row-level-security), [함수 실행 권한](https://supabase.com/docs/guides/database/functions), [서버 API 키와 헤더](https://supabase.com/docs/guides/getting-started/api-keys). 특히 서버 secret key는 RLS를 우회하므로 별도의 사용자 소유 관계 검사가 필요하고, 함수 권한은 기본값에 맡기지 않는 설계로 반영했다.
